# Gemmini 学习笔记：从软件指令到硬件电路与矩阵数据流

> **学习主线**：以一条 Gemmini 指令为入口，沿着「应用软件 → 软件库 → ISA → 硬件」的 3.5 层框架，追踪矩阵加载、片上存储、脉动阵列计算、部分和累加、激活及写回；再研究大矩阵分块、双缓冲和 WS/OS 数据流的架构权衡。
>
> **说明**：文中反复使用一组便于计算的示例配置：`DIM=16`、输入 `int8`、4 个 Scratchpad Bank、每个 Bank 为 `4096×128 bit`，合计 256 KiB。Gemmini 是可参数化架构，具体芯片的阵列、端口、容量、流水线延迟和带宽取决于所采用的配置。本笔记中的简化电路、伪代码用于说明硬件机制，并非完整的 RTL 或门级网表。

## 一、软硬件 3.5 层框架：每一层负责什么

我们首先建立的框架不仅适用于 Gemmini，也适用于 CPU、GPU、NPU 等可编程计算系统。关键不是把所有东西称为“指令”，而是区分**应用需求、软件策略、指令规则和硬件实现**。

| 层次 | 核心职责 | Gemmini 中的实例 | 主要由谁设计 |
|---|---|---|---|
| ① 应用软件 | **要完成什么运算** | 计算 `C=A×B`，可能再执行 ReLU | 应用开发者 |
| ①.5 软件库 | **如何组织任务** | 分块、循环顺序、数据复用、选择片上地址、安排加载和计算 | 软件库开发者 |
| ② 指令集架构（ISA） | **软硬件如何交互** | `mvin`、`preload`、`compute`、`mvout`、配置指令等的语义及参数 | 体系结构设计者 |
| ③ 硬件微架构 | **如何实际完成操作** | 译码器、RoCC 接口、状态机、DMA、SRAM、PE、Accumulator | 硬件设计者 |

**编译器是上述各层之间的重要转换环节**：把 C/C++ 程序及指令接口宏编译为 CPU 可执行的机器指令。ISA 本身不是一个单独执行任务的电路，而是软件与硬件共同遵守的契约。同一种 ISA 可以由不同的微架构实现。

我们反复使用的调用是：

```c
// 对于按行连续存放的 int8 矩阵，主存行跨度需先正确配置
for (int r = 0; r < 32; r += 16) {
    gemmini_extended_mvin(&A[r][0], r, 16, 16);
}
```

`gemmini_extended_mvin` 的四个参数依次为：**主存起始地址、片上存储起始行地址、列数、行数**。`r=0` 和 `r=16` 时，软件分别要求加载矩阵 A 的前 16 行和后 16 行。这两条加载命令是 **CPU 在运行 C 循环时发出的**，不是第一条 `mvin` 自己创造第二条指令。相反，一条合法 `mvin` 内部如何分多次完成 DMA 搬运，是由硬件预先设计好的执行机制负责。

因此，**软件库定义大问题的组织策略，ISA 定义单条操作的规则，硬件按规则执行**。当矩阵超过 Scratchpad 容量时，软件需要规划分批加载、计算和空间复用；硬件并不会观察到“Bank 满了”就临时产生一套通用矩阵分块算法。Gemmini 另外提供高级硬件循环接口（例如 `gemmini_loop_ws`），可以在规定的资源范围内，把较大的矩阵任务展开成多次加载和计算；这并不改变 3.5 层的职责划分。

## 二、`mvin` 完整路径：译码、DMA、总线、Bank 与 SRAM

这是我们分析最深入的部分。固定下面的任务：A 是 `16×16` 的 `int8` 矩阵，C 程序以行优先方式将它放在主存，起始地址假定为 `0x80000000`；软件已配置主存行跨度 `stride=16 Byte`，片上目标行地址为 0。最终将 256 Byte 写到 **Bank 0 的第 0—15 行**。

整体执行链为：

```text
C 程序 / 软件库
    ↓  编译成 CPU 自定义机器指令
CPU 译码器
    ↓  RoCC：funct、rs1、rs2、valid/ready
Gemmini 译码、预约站（Reservation Station）
    ↓  LD 命令
LoadController（状态机 + 行计数器 + 地址生成）
    ↓  DMA 逐行读取请求
DMA 读入器与 TileLink 存储互联
    ↓  返回数据 + 本地目标地址 + 有效掩码
Scratchpad Bank 译码与写入仲裁
    ↓
Bank 0 的 SRAM 第 0—15 行
```

**CPU 的指令译码和 Gemmini 内部译码是两次不同的工作。** RISC-V 自定义指令字通常为 32 bit，其中记录 `opcode`、`funct`、`rs1/rs2` 的**寄存器编号**等字段；矩阵起始地址和打包后的尺寸参数属于 CPU 寄存器里保存的操作数，并非都直接装进 32-bit 指令本身。CPU 的组合译码逻辑识别自定义 `opcode`，读取相应通用寄存器，把命令通过 RoCC 接口送到 Gemmini。

本例操作数可以理解为：

```text
rs1 的值 = 0x80000000             // 主存源地址
rs2 的值 = 0x0010001000000000     // 行数16、列数16、片上地址0
funct    = 2                      // Gemmini 的 mvin
```

在标准单元层面，检查 `funct=2` 就是对七位编码 `0000010` 做相等比较。它可以综合为反相器、AND/NAND 等组合逻辑。Gemmini 依据译码结果将命令分给加载（LD）、执行（EX）或存储（ST）通路；预约站检查依赖并将加载命令送给 LoadController。译码器**不会分析矩阵的数学意义**，只依照固定的比特编码产生控制信号。

### LoadController：地址计算和状态控制为什么是两回事

LoadController 使用一个行计数器。为避免与 C 循环的变量 `r` 混淆，记硬件行计数器为 `k=0,…,15`。它每次产生一行的 DMA 请求：

\[
\begin{aligned}
\mathrm{DRAMAddr}(k)&=0x80000000+16k,\\
\mathrm{LocalAddr}(k)&=0+k,\\
\mathrm{Cols}(k)&=16.
\end{aligned}
\]

| `k` | DRAM 起始字节地址 | Scratchpad 存储行地址 |
|---:|---|---:|
| 0 | `0x80000000` | 0 |
| 1 | `0x80000010` | 1 |
| 2 | `0x80000020` | 2 |
| … | … | … |
| 15 | `0x800000F0` | 15 |

主存地址每次加 16，是因为**主存按 Byte 编址，矩阵一行包含 16 Byte**；片上地址每次加 1，是因为**此示例的 Scratchpad 逻辑地址按 128-bit 存储行编址，每个地址本来就对应 16 Byte**。这不意味着 DRAM 的物理阵列行也是 16 Byte。所谓矩阵行，是 C 程序对数据的逻辑排布；DMA 按已配置的行跨度将源字节序列映射到目标存储行。

硬件里的加法器负责计算下一行地址，行计数器保存进度，状态机决定何时发送、等待和结束。对于每个请求，LoadController 和 DMA 使用 `valid/ready` 握手：

\[
\mathrm{request\_accepted}=valid\land ready.
\]

请求未被接收时，不能直接把计数器加一，否则会跳过某行。一个典型的计数器更新关系为：

\[
k_{\mathrm{next}}=
\begin{cases}
k+1,&\text{当前行请求被接收},\\
k,&\text{否则。}
\end{cases}
\]

这说明了我们对**状态机（FSM）**的理解：状态机不是某种有智能的特殊器件，而是由状态寄存器（DFF）和下一状态组合逻辑构成；计数器、比较器、MUX 和握手信号共同协调多周期操作。不是每条硬件指令都各有一个 FSM，例如普通 ALU 加法可通过组合逻辑和流水线寄存器完成；DMA 控制器这种需要等待外部响应的模块通常要有时序控制。

### 总线与 DMA：从请求到真实数据

我们区分过两种总线分类方式：**按用途**可以称为存储总线、外设/控制总线、内部数据通路；**按协议**有 TileLink、AXI、APB 等。用途分类并不意味着一定对应完全独立的物理布线，现代 SoC 常有共享互联、桥接器、仲裁器和多级网络。

Gemmini 通过 DMA 的 TileLink 接口访问存储系统。DMA 收到 LoadController 的内部请求后，处理地址翻译（TLB）、生成 TileLink 读取请求，经总线互联访问缓存或主存，并接收响应。TileLink 请求与响应使用不同通道；每条通道包含地址/数据/控制字段和握手信号。CPU 不需要为每个数据拍再执行一条指令。

DMA **不是一根简单的导线**，内部还需要请求寄存器、事务跟踪器、缓冲/FIFO、计数器、数据拼接器、位移选择器、字节掩码等电路。若读入地址与存储行宽对齐，16 Byte 可以直接作为一个 128-bit 数据字写入；若地址未对齐，例如从偏移 4 Byte 处读取 16 Byte，可能要跨两个对齐数据拍：

\[
D=\{Beat_1,Beat_0\},\qquad
Data_{out}=(D\gg32)[127:0].
\]

这里的拼接与移位由寄存器、组合逻辑和 MUX 完成，不是 CPU 在逐字节执行指令。DMA 整理出的结果可包含 `data[127:0]`、目标 `laddr`、写入有效掩码和 `valid`。**位宽重组只改变物理分组方式，不丢失数据**：来自 DRAM 的 16 个 8-bit 元素，按照规定的字节顺序填入 Scratchpad 一行的 128 bit。

### Bank 译码与真实 SRAM 写入

固定 4 个 Bank，每个 Bank 为 `4096×128 bit`。每个 Bank 有 4096 行，需要 12 bit 行地址；4 个 Bank 需要 2 bit Bank 编号。因此在我们的示例中，片上存储行地址可写作：

\[
\underbrace{a_{13}a_{12}}_{\text{Bank ID}}\;
\underbrace{a_{11}\cdots a_0}_{\text{Bank 内行号}}.
\]

`a_i` 就是**本地地址的第 i 个二进制位**，不是矩阵 A 的元素。例如：

\[
Select_0=\overline{a_{13}}\land\overline{a_{12}}.
\]

| Local Address | Bank | Bank 内行号 |
|---:|---:|---:|
| 0 | 0 | 0 |
| 4095 | 0 | 4095 |
| 4096 | 1 | 0 |
| 8192 | 2 | 0 |
| 12288 | 3 | 0 |

这种选择由简单的组合地址译码逻辑完成。Bank 接收到行地址、128-bit 数据、写使能和有效掩码后，内部 SRAM 行译码器激活目标字线（Wordline），写驱动器通过位线（Bitline）写入存储单元。

硬件实现还应区分：**译码器、计数器、MUX、控制器等通常综合为标准单元（Standard Cells）；SRAM 阵列及行译码/位线外围通常属于 SRAM 宏单元（SRAM Macro）**，不是把每个存储位都做成普通 DFF。软件中看到的“写一个矩阵行”，最终对应真实存储宏上的地址端口、数据端口、写使能和时钟控制。

### 不同矩阵大小对应什么处理层级

最重要的是分清**单条搬运指令上限、单个 Bank 容量、整个 Scratchpad 容量和脉动阵列计算尺寸**。

| 矩阵大小 / 情形 | 主要处理方式 |
|---|---|
| 8×8 | 一条 `mvin`，行数参数为 8 |
| 16×16 | 一条 `mvin`，行数为 16 |
| 32×16 | 软件组织至少两条 `mvin`，每条最多 16 行 |
| 16×32 | 在支持相应列数的配置下，一条 `mvin` 可以跨两个 16 列块搬运，目标地址由 `block_stride` 等参数控制 |
| 本地地址跨 Bank 边界 | 存储端按目标地址自动完成 Bank 译码，不是“发现 Bank 满了再分配” |
| 数据总量超过 Scratchpad | 软件（或其调用的高级循环机制）规划分批加载、计算和存储空间复用 |

这里 `mvin` 的行数限制采用 `DIM=16`，**不是因为 SRAM 行宽为 16 Byte**。SRAM 行宽影响单次目标存储行能接收多少个元素；`DIM` 规定基础搬运指令的行高度限制。16×32 的两列块可按预设间距写入连续片上存储行，例如分别写入 LocalAddr 0—15 和 16—31。

最后，我们还解释了 **32-bit Gemmini Local Address**：它不仅编码行地址，也复用高位表达存储空间和操作模式。`bit31` 区分 Scratchpad 与 Accumulator；`bit30` 在写 Accumulator 时区分覆盖与累加；`bit29` 在读 Accumulator 时参与高精度/缩放结果选择。譬如 `0x80000000` 与 `0xC0000000` 指向同一 Accumulator 物理起始行，差别是后者要求累加。**这一 32-bit 本地地址，不等于主存的字节地址，也不等于累加数据的 int32 位宽。**

## 三、大矩阵：存储分块、计算分块、数据复用和双缓冲

我们发现“Tile”至少有三个不同尺度：**搬运分块**（由指令和 DMA 的搬运能力约束）、**存储分块**（由 Scratchpad 容量和复用策略约束）、**计算分块**（由 16×16 脉动阵列尺寸约束）。它们相互关联，但不要求大小相同。

例如，计算：

\[
C_{1024\times1024}=A_{1024\times1024}B_{1024\times1024}.
\]

输入采用 int8，A 和 B 各为 1 MiB，显然都无法整个放进 256 KiB 的 Scratchpad。最初为了直观，我们取 A 的 `64×256` 块与 B 的 `256×64` 块，每块 16 KiB，合计 32 KiB。随后讨论了更充分利用容量的方案：

\[
A_{tile}:128\times512=64\,KiB,\qquad
B_{tile}:512\times128=64\,KiB.
\]

两块输入合计 128 KiB，正好是两个 Bank 的容量，也就是一个 Ping-Pong Buffer 的全部容量。它们贡献一个 `128×128` 输出块在长度 512 求和维度上的部分结果；完整求和长度为 1024，还要处理下一段：

\[
C_{tile}=A_0B_0+A_1B_1.
\]

同时，`128×512` 与 `512×128` 仍不能直接一次送入 16×16 阵列。这一批次需要：

\[
\frac{128}{16}\times\frac{128}{16}\times\frac{512}{16}=2048
\]

次 16×16 子矩阵乘法，得到一个 128×128 的**部分输出块**。若以 int32 保存，完整的 128×128 输出块需要 64 KiB 的 Accumulator 空间，这又是独立于输入 Scratchpad 的容量约束。

外层调度的核心逻辑可用下面的 **C 风格伪代码** 表示（并非可直接编译的 Gemmini API）：

```c
for (int i = 0; i < 1024; i += 128) {
    for (int j = 0; j < 1024; j += 128) {
        prepare_accumulator_for_output_tile(i, j);

        for (int k = 0; k < 1024; k += 512) {
            load_A_tile(i, k, 128, 512);
            load_B_tile(k, j, 512, 128);
            compute_16x16_products_and_accumulate();
        }

        write_completed_C_tile_to_DRAM(i, j);
    }
}
```

这里的 `i/j` 确定**输出 Tile 放哪里**，`k` 沿矩阵乘法的求和维度前进；具体代码库可以进一步改变循环顺序，以提高 A 或 B 的复用率。`load_A_tile`、`load_B_tile` 可以展开为多条合法 `mvin`；内层计算可由软件展开 `preload/compute`，或由高级硬件循环展开器处理。

**先把多个输入 Tile 加载进 Scratchpad，再执行许多 16×16 计算，往往比每做一次小乘法就重新访问 DRAM 更好。** 我们用 32×32 例子比较过：一种最朴素的逐乘法加载顺序需要读取 16 个 16×16 输入块次，而先加载 A/B 的全部八个不同子块、再复用它们，只需要 8 块次；总乘法次数同为 8 次。对于 int8 输入，这个具体示例的 DRAM 输入搬运量从 4096 Byte 降到 2048 Byte。

**Ping-Pong（双缓冲）**则进一步把两个阶段重叠。对于四个 64 KiB Bank，可以用两个 Bank 保存当前 A/B 块，另外两个 Bank 加载下一批 A/B；下一轮互换角色。理想稳态下，每批执行时间约为：

\[
T_{batch}\approx\max(T_{load},T_{compute}).
\]

这只是理想重叠模型，不代表两者一定完全并行。是否发生 Bank 冲突，取决于数据读写是否竞争同一个端口；在单端口 Bank 的情况下，同时读写同一 Bank 需要仲裁。若当前计算与下一批加载使用不同 Bank，就能避开这类直接冲突。

我们还讨论过“为什么不把两个 128 KiB Buffer 都填满”。**填满本身没有错**，但可能没有给临时数据和额外预取留下空间，而且更大的 Tile 不自动意味着更好的吞吐率。真正要比较的是数据复用、DRAM 传输量、Scratchpad/Accumulator 容量、读写端口冲突、加载与计算是否匹配。不能把“DMA 变慢”误解成“相同矩阵突然需要四倍乘加”；它增加的是等待时间，而不是数学计算量。

这里还出现了一个概念上的重要进展：**存储占用、计算阵列占用不是一回事**。一个 Buffer 正被计算任务使用，意味着数据从 SRAM 中逐步读出并送到阵列，而不是整批数据都被转移进 256 个 PE。计算期间不能覆盖那些尚未被读取的数据。

## 四、`preload`/`compute`、PE 寄存器与 WS/OS 数据流

加载完成后，数据流从主存搬运切换为片上计算：

```text
Scratchpad 中的 B
    ↓ preload（WS）
PE 内部权重寄存器
    ↑
Scratchpad 中的 A → compute → PE 的乘加与部分和传播
                                   ↓
                               Accumulator
```

### `preload` 怎样用 128-bit SRAM 读口填充 256 个 PE

这也是我们专门深入到互联的一段。B 是 16×16、共有 256 个 int8，SRAM 一次读出 128 bit = 16 个 int8。因此不可能只用一个 128-bit 数据拍就填满 256 个 PE。Gemmini 在 WS 模式下使用**逐行读取、适当的逆序装载、PE 之间的纵向传播、寄存器锁存**，把权重逐步分布到对应的处理单元。`MeshWithDelays` 还会为不同数据通路及控制信号插入所需的延迟，使它们在正确时钟周期抵达正确的 PE。16 轮有效行输入对应全部 16×16 数据量；实际装载完成延迟还包含 SRAM 读时延及阵列/Tile 流水线延迟。

PE 不是一块只能读一个固定 SRAM 地址的存储器。它具有真实的寄存器、选择器、MAC 运算逻辑以及相邻 PE 之间的连线。我们重点研究了 Gemmini 的两个权重相关寄存器 `c1`、`c2` 和一个控制位 `propagate`（简称 `prop`）：

| `prop` | c1 | c2 |
|---:|---|---|
| 0 | 保持并作为当前 MAC 的权重 | 接收、向下传播新权重 |
| 1 | 接收、向下传播新权重 | 保持并作为当前 MAC 的权重 |

例如当 `valid=1, prop=1` 时，可用简化寄存器关系理解为：

\[
\begin{aligned}
c_1^{next}&=d_{in},&c_2^{next}&=c_2,\\
W_{MAC}&=c_2,&d_{out}&=c_1^{old}.
\end{aligned}
\]

关键是 `d_out` 传给下一个 PE 的，是寄存器在该时钟沿更新**之前的旧值**。硬件不会根据权重的数值判断哪些留下、哪些传播，而是通过 `prop` 控制寄存器使能与两个 MUX 的选通。

你提出过“一组寄存器 + 一路输入选择器是否就够了”。我们明确了：**单寄存器完全能够完成最基本的 WS 计算，但没法在保留旧权重给 MAC 使用的同时，再把新权重写进同一个寄存器。** 两个寄存器提供了寄存器级 Ping-Pong：一组为当前 MAC 保存旧 B，另一组接收下一批 B；之后互换。这与 Scratchpad 的双缓冲在思想上相同，但分别发生在不同的硬件层级。

**权重驻留的复用**也得到了具体解释。假设：

\[
A_{32\times16}B_{16\times16}=C_{32\times16}.
\]

将 A 分成 `A₀`、`A₁` 两个 16×16 块，则 `C₀=A₀B`、`C₁=A₁B`。WS 可以先装载一次 B，然后让 A₀ 和 A₁ 先后进入阵列，两次计算都复用同一组 PE 权重寄存器。在 Gemmini 的 WS 语义下，`compute.accumulated` 可继续使用此前装载的权重；它的名称**不等同于**“专门让外部 Accumulator SRAM 做一次累加”。

### WS 和 OS 比较：优化的数据移动并不相同

| 对比维度 | WS：权重固定（Weight-Stationary） | OS：输出固定（Output-Stationary） |
|---|---|---|
| PE 内主要保持什么 | B 的权重 | C 的部分和 |
| 主要流动的数据 | A 与部分和 | A 与 B |
| 哪一种数据可大量复用 | 当前 B 块 | 当前 C 块的部分和 |
| 跨块部分和 | 主要在外部 Accumulator 中处理 | 可以继续保留在 PE 内累加 |
| 典型代价 | 部分和在阵列外的数据移动 | 权重反复送入阵列 |

对于分块乘法：

\[
C_{ij}=\sum_k A_{ik}B_{kj},
\]

**WS 倾向固定 `k,j`，遍历不同 `i`**：例如固定 `B₀₀`，依次计算 `A₀₀B₀₀` 与 `A₁₀B₀₀`，这会生成属于 `C₀₀` 和 `C₁₀` 的两个不同部分和，不能互相相加，必须保存到不同输出位置。之后换成 B₁₀，再去补全这两个 C 块。

**OS 倾向固定 `i,j`，沿求和维度 `k` 前进**：例如对 `C₀₀=A₀₀B₀₀+A₀₁B₁₀` 连续计算，部分和可以保留在 PE 的累加寄存器内，但 B 需要随计算再次进入阵列。注意**B 重新进入 PE，不代表再次从 DRAM 取 B**；它可能仍保存在 Scratchpad。

我们因此发现：WS 减少权重输入流量、OS 减少部分和移动量，但它们的实际收益不能只按“数据块次数”判断，因为 B 常为 8 bit、部分和常为 32 bit，不同层级 SRAM、寄存器和 DRAM 的带宽、能耗和延迟也不同。真正应联合优化的是**数据流选择 + Tile 尺寸 + 循环顺序 + 片上存储容量/端口**。同样大小的运算，两种模式可具有相近峰值 MAC 吞吐，但启动、装载、排空、存储压力和实际利用率会不同。

## 五、结果阶段：Accumulator、拼接、`mvout`、激活函数与 Softmax

### 部分和累加：由目标地址规定覆盖还是累加

在 WS 模式下，一次 16×16 矩阵乘法完成后，阵列沿结果通路输出部分和，送到独立的 Accumulator。Accumulator 不是纯 SRAM，而是一套**SRAM + 并行加法器 + 写入选择器 + 冲突控制**的存储系统。对于 `accType=int32, DIM=16`，一行可包含 16 个 int32，总数据宽度为 512 bit；相应累加路径可以按多个元素并行执行 32-bit 加法。

我们以：

\[
C_{00}=\underbrace{A_{00}B_{00}}_{P_0}+\underbrace{A_{01}B_{10}}_{P_1}
\]

为例。首次计算 `P₀`，直接写入 Accumulator；第二次计算 `P₁`，读出同一个地址的 `P₀`，计算 `P₀+P₁` 后写回。后续多次累加也重复这套**读—改—写（Read–Modify–Write）**流程；读写的是**片上 Accumulator SRAM**，不是每轮都回 DRAM。

| 次数 | 对同一输出地址的操作 |
|---:|---|
| 首次 | `Acc[X] ← P₀`（覆盖） |
| 第二次 | `Acc[X] ← Acc[X]+P₁` |
| 第三次 | `Acc[X] ← Acc[X]+P₂` |

实际调度通过 `preload` 的目标输出地址携带模式。在 WS 模式下，`preload` 指定 B 的输入位置和 C 的输出位置；随后的 `compute` 产生结果，结果写入 Accumulator 时按地址控制位执行：

```text
0x80000000：bit31=1，bit30=0  → Accumulator 起始行0，覆盖
0xC0000000：bit31=1，bit30=1  → Accumulator 起始行0，累加
```

例如 `Acc[100]=120`，新部分和 `P₁=30`：先读 120，经加法器算出 150，再写回原地址 100。选择器决定写入 `New` 还是 `Old+New`。**`preload` 指定写入位置和模式，`compute` 产生计算数据，而 Accumulator 硬件执行真正的累加**。

如果前一轮对地址 X 的写入尚未结束，新一轮就访问同一个 X，会有读后写/写后写依赖问题；Accumulator 控制电路因此需要未完成写入记录、地址比较、流水线寄存器、就绪信号及必要的停顿或旁路机制。它也需要处理同一 Bank 的端口冲突。

这里我们区分了两种“立即累加”：其一是连续计算同一个输出块并立即在 Accumulator 更新；其二是让 PE 内的部分和完全不出阵列。**前者 WS 可以做到，但通常仍有 Accumulator SRAM 的读写；后者是 OS 输出驻留更直接的优势**。如果为了固定 B 而依次计算不同输出块，部分和就必须分别保存在不同位置，等待后续贡献到来。

### 小矩阵如何组成大矩阵：区分“累加”和“拼接”

例如 32×32 的输出：

\[
C=\begin{bmatrix}C_{00}&C_{01}\\C_{10}&C_{11}\end{bmatrix},
\qquad C_{ij}\in\mathbb{R}^{16\times16}.
\]

**同一位置的乘积贡献要累加，不同位置的完成块只需要正确编址。** 在 Accumulator 中可以把四个块分别放在不同的存储行区域；当 `mvout` 写回行优先的 DRAM 矩阵时，用正确的目标偏移和行跨度实现拼接，而不需要额外的“拼矩阵运算器”。例如输出为 int8、每行 32 Byte 时：

| 输出块 | 在最终 C 中的位置 | DRAM 起始字节偏移 |
|---|---|---:|
| C₀₀ | 行 0–15、列 0–15 | 0 |
| C₀₁ | 行 0–15、列 16–31 | 16 |
| C₁₀ | 行 16–31、列 0–15 | 512 |
| C₁₁ | 行 16–31、列 16–31 | 528 |

以 C₀₀ 为例，每次写回一行 16 Byte，但主存目标的下一行要跨过 32 Byte：

\[
DRAMAddr(r)=CBase+32r.
\]

如果 C 大到 Accumulator 也放不下，就计算完成一个或若干个输出块，写回 DRAM，再复用片上结果空间。**“物理拼接大矩阵”与“把完成的小块写到大矩阵正确地址”是两回事。**

### 激活函数与量化：为什么 ReLU 可以放进 `mvout` 数据通路

在 WS 模式下，结果典型路径为：

```text
Accumulator SRAM（int32 部分和已完成）
    ↓  读出
激活电路 / 缩放器 / 舍入和位宽转换
    ↓
StoreController 与 DMA
    ↓
DRAM 中的最终输出（例如 int8）
```

软件通过配置指令预设激活模式、缩放系数及输出行跨度；后续 `mvout` 触发读出和写回，结果在途中通过这些电路。因此 `mvout` 仍是输出搬运指令，但可以**融合**一部分逐元素的输出处理，不需要给 ReLU 单独设计一条 CPU 式运算指令。Gemmini 对 WS 结果输出的 ReLU 配置主要关联存储/Accumulator 读出路径，而 OS 数据流也有与执行通路相应的激活配置。

ReLU 的规则是：

\[
y=\max(0,x).
\]

对于有符号 32-bit 补码，最高位 `x[31]` 是符号位，负数时为 1。因此可用组合逻辑：

\[
y_i=x_i\land\neg x_{31}.
\]

激活使能加入后，可写成 `y_i = x_i AND NOT(relu_enable AND x[31])`。一组门电路或 MUX 就能完成，不需要复杂状态机或跨元素通信。若最终写回的是量化后的 int8，还要考虑缩放系数、舍入与饱和裁剪等外围电路。**ReLU 应在同一个输出元素的全部求和贡献完成后执行**；例如 `ReLU(-5+10)=5`，但若对第一项提前激活，`ReLU(-5)+10=10`，结果错误。

### Softmax 为什么不同：跨 Tile 的统计与调度

Softmax 定义为：

\[
y_i=\frac{e^{x_i}}{\sum_j e^{x_j}}.
\]

ReLU 仅依赖一个元素，Softmax 的分母则依赖**整个归一化范围**。如果输出矩阵为 1024×1024，采用按行 Softmax、计算 Tile 为 16×16，那么一行跨越 `1024/16=64` 个 Tile：**不能对每个 Tile 分别执行独立 Softmax**。

但这不意味着必须在物理存储中把所有 Tile 拼成一个巨大矩阵。可以依次读取 Tile，跨 Tile 维护同一行的最大值及指数和，然后在第二遍读取或缓存的数据上完成归一化。典型数值稳定写法为：

\[
m=\max_i x_i,\qquad S=\sum_i e^{x_i-m},\qquad y_i=\frac{e^{x_i-m}}{S}.
\]

因此 Softmax 会引入归约比较器、指数近似、加法归约、倒数或除法、统计寄存器，以及跨 Tile 的调度和数据缓存。LayerNorm 等全局统计型算子也有类似的跨元素依赖。我们由此理解了：**能否自然融合进一条数据搬运路径，关键不仅是函数电路有多复杂，更重要的是每个输出是否依赖其他元素。** 对 Attention 中的 Softmax，统计范围通常对应同一 Query 的全部有效 Key，而不是一个固定的 16×16 计算 Tile。

## 六、现阶段的学习重点与下一步

回顾整个过程，我们已经不只是认识 Gemmini 的指令名，而是建立了从软件需求到门级动作、从 DRAM 数据布局到 PE 计算、再到结果写回的完整因果链。下面把学习成果和仍需深入的内容合并在一张表中：

| 主题 | 已经理解的核心 | 下一步最值得进一步追踪的问题 |
|---|---|---|
| 3.5 层职责 | C 应用提出任务；软件库组织策略；ISA 是契约；硬件执行 | 编译后的一段真实机器指令如何与库函数逐一对应 |
| CPU / RoCC / Gemmini 译码 | `opcode`、`funct`、寄存器操作数、`valid/ready` 和 LD/EX/ST 分发 | 从 RTL 追到译码标准单元及实际互联 |
| LoadController / DMA | 状态机、地址生成、行计数器、总线协议、数据拼接 | DMA 一次真实事务的逐周期波形和总线拍数 |
| Scratchpad / Bank | 128-bit 行宽、4096 行、Bank 地址译码、SRAM 宏单元 | 端口仲裁、同 Bank 冲突、布线层级与负载 |
| 大矩阵分块 | 搬运 Tile、存储 Tile、计算 Tile 是三个尺度；软件/硬件循环协同 | 外层 Tile 大小与带宽、容量、利用率的量化关系 |
| 双缓冲 | Scratchpad 级隐藏主存延迟；PE 寄存器级隐藏权重装载 | 对照时序图判断何时真正重叠、何时只能等待 |
| PE 与数据流 | `preload/compute`、MAC、`c1/c2`、`prop`、WS/OS | 单 PE 的真实组合逻辑、寄存器数量和时钟关键路径 |
| Accumulator | 覆盖/累加地址位、原位读—加—写、相关冲突 | 同地址连续写入的流水线细节、是否停顿与吞吐瓶颈 |
| 输出与激活 | `mvout`、DMA 行跨度、量化、ReLU、Softmax 跨 Tile 统计 | 非线性函数电路成本和整行归约的实现调度 |

下一阶段最合适的主线是**时钟周期级执行（Cycle-Accurate Execution）**：选取一次真实的 `mvin → preload → compute → Accumulator → mvout`，逐周期记录指令进入、地址请求发出、数据返回、PE 更新、部分和写入和输出完成的时间点；再结合 SRAM 单/双端口、DMA 带宽和 PE 流水线，建立可信的性能模型。等这些关系清楚以后，再进入 RTL 仿真、门级网表和布局布线，才能解释“哪些线连接 Bank、哪些线连接 PE、哪些线承担控制和总线功能”。

**总体学习结论**：我们最重要的进展，是理解了“指令不是硬件的智能决策，而是触发预先实现的控制电路和数据通路”；在此基础上，开始能够从数据移动、存储容量、寄存器复用与时序冲突的角度讨论真正的硬件架构设计。
