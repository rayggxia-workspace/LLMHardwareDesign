# Issue98：先解释工具停止原因，再增加有限修复预算

93 原 CTS 在传播时钟下有 1,057 个 hold 违例。候选1采用 0.005 ns 修复裕量、两个上限均为1，插入1,441个hold缓冲后剩238条，全部来自输入到FF。候选2把修复裕量增到0.125 ns，面积从57,918.840增到59,390.352 μm²，却仍剩237条、最差延迟完全相同；不能继续盲增裕量。

服务器 `same-path9301` 对同一 `ext_data[79]→_70796_/D` 路径逐pin重测：C1/C2都包含hold771/772/773三个CLKBUF_X1，数据到达0.140675396 ns，时钟到达0.241822347 ns，要求0.252273023 ns，slack −0.111597620 ns。C2多出的975个仅由FF输出驱动的缓冲并未修好该路径。两候选完整功能、几何、电气和setup通过，但hold未闭合，不能宣称物理通过。

使用Liangruizhi认证只读核对[实际工具commit的RepairHold.cc](https://github.com/The-OpenROAD-Project/OpenROAD/blob/63ed2e0fe5/src/rsz/src/RepairHold.cc)。SHA-256为`abbbfd4758fdbc32d7e19cad3dc060b2bffae03efb6c1d6e704ba28ce57619c3`，未安装或编译新工具。该版本在一批端点内逐端点增加计数，在批结束后的外层while才检查两个上限。因此上限1已经处理完整首批1079端点，但阻止再次处理仍不足的路径；把它改成2或4也仍不足。不能套用最新master文档来猜本机旧版行为。

候选3恢复C1的0.005 ns修复目标，仅将max_passes和max_iterations固定为4096，从原CTS重新运行同三步。4096是批间检查的累计端点预算，末批可能超出计数，不称4096轮；10%新增缓冲、79,600.5 μm²、20分钟/8CPU及原时钟/IO/全接口仍共同约束。候选1、2失败保留。93和97均使用各自实际原CTS；C1→C3只解释有限修复预算影响，不归因于Block划分创新。若仍失败，保留原因，不自动扩大预算或改验收门槛。
