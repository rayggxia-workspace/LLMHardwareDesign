# PR220 / PR241 的 token/s 提升路径研究

2026-11-09，Asia/Shanghai；负责人 Melodydt。[Issue #244](https://github.com/rayggxia-workspace/LLMHardwareDesign/issues/244) / [PR #243](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/243)。按用户指定复用当前分支；原 #242 LOAD 修复保留，研究单独跟踪。

## 结论与优先级

现有硬件路线应先改善数值配方、有限S驻留和真实打包供数；PR241的新硬件候选路线则应集中优化P/DMA的供数与流量。两条路线分别验收，不能将候选S32宏当作当前能力。继续增加搜索宽度没有证据能解决数量级差距。保持独立叶宏、局控归属和M11/M12后制互联；新增算术、缓存或端口需新RTL/物理资格。

本研究期间上游有更新，已在2026-11-09 05:31 UTC重新读取：PR220为 `bf31827f7e039038ca2547046a13d29c4bf46901`（迭代15），PR241为 `e7aeed2097f57a5f910cae70eb51a220c49a8a14`（新增34组SystemC场景）。下节以新结果确定下一轮重点；旧版本作为固定对照，排队作业不混用新输入。

## 最新 PR241：下一轮的两个硬门槛

最新模型只激活P0/P1/U0，假设原生S32 M、E32和512位接口，每组S仍16KiB。W8权重、S32激活/KV、context512的条件decode为 **2.714625 token/s**；W16对照为 **1.682081**。它是上游Windows/SystemC架构预测；完整新量化/KV数值、新RTL/物理和Linux完整sweep均未验收，不等于当前三颗原生S8 M的生成成绩。

本分支固定34组原始结果，算术、时间换算、容量及阶段守恒核验 **34/34通过**，没有重新执行这34组SystemC。[量化结果](../../work/Melodydt/244/latest-systemc-assessment.json) · [上游原始记录](../../work/Melodydt/244/upstream241-results.json)。

最终候选每token总线字节为 **3,604,728,064 B**，Dot及供数/回写占 **83.1895%**。17.1GB/s是参考聚合峰值，非本项目已校准外存。保持该流量时，`token/s ≤ BW/bytes = 4.743770`。原模型逐算子串行阶段中的其他阶段约0.061926秒，因此：

| 目标 | 原流量所需最低聚合峰值 GB/s | 保持17.1GB/s时最低减流量 | 其他阶段不变时Dot服务至少提速 |
| --- | ---: | ---: | ---: |
| 4 token/s | 14.4189 | 0；仍需改善利用率与停顿 | 1.6294× |
| 5 token/s | 18.0236 | **184,728,064 B/token（5.1246%）** | **2.2195×** |
| 10 token/s | 36.0473 | 1,894,728,064 B/token（52.5623%） | 8.0487× |

这些是必要条件，不是可同时达到的预测。仅将Dot时长减半还不够达到5；其他阶段即使全部免费、Dot不变，上限也仅约3.2632token/s。应优先处理P供数和流量，而非继续单独增大E队列或DP宽度。

下一轮应按以下配置做独立消融：

1. **先补可归因计数。** 同一W8/W16模型分通道记录读写字节、bus busy、S等待、bank/row/换向、描述符等待、P生产/消费气泡。全程平均9.79GB/s约为参考峰值57.2%，不能直接推断带宽富余或增加credit即可；目前聚合字节不能定位通道。
2. **消除仍重复的搬运。** 比较输出直接形成下一消费者布局、跨元素保留常量/保护字/B银行、有限S驻留及合法连续描述符。W8一次权重流约3.085697GB；context512理想GQA的S32 KV读/追加分别37,748,736/73,728B。当前总线比这三项之和多约481.209MB，先追踪来源，不承诺全部可删。减184.728MB只是5token/s的带宽门，仍须改善Dot停顿。
3. **检验第三个P，保持总线预算。** 新模型 `mcount=2`，项目清单有三个P，可做2P/3P消融并明确私有S与通道。第三P采用候选S32服务仍须计入宽算术/接口资格，不能继承现有P2的S8资格。若两个P落在同一通道，均分列可能失衡，应比较按通道负载分列，保持完整K、最终舍入、ACK和静态连接预算，不能直接宣称1.5倍。
4. **保留退化对照。** 同精度context512，从输入驻留的 `stream_p_w8_resident`（2.2740）改为 `queued_p_w8`（2.2201）反而变慢，再加E32流水才到2.7146。队列不是越深越快；所有合法新能力须提供给全部调度基线，后端/硬件与算法收益分账。
5. **10token/s需要更强改变。** 仅把W8权重改成W4、其他字节不变时，流量情景仍约2.061880GB/token，17.1GB/s下上限约8.2934，仍不足10；且W8/W4量化未资格化。分别评估质量合格的低比特、更多有效复用或更高接口预算，不能拼接不同模型/精度的FPGA结果宣称达标。

## 冻结基线和指标边界

- 原PR220固定对照：`532240d46f7c747aafe70563ffda23866e09cf37`，迭代14。该版完整搜索计划167,410,668,834模型ticks，较此前已验计划少172,032（约0.00010276037%）。迭代15已报告该旧计划三输入数值终态通过，未给新驻留动作转移资格。
- 原PR241诊断版本：`047da9029ec23e4974961cb4f579207d8bcaff3c`。其attempt277的conditional-DP为167,410,840,866ticks，资源/依赖图和服务级SystemC已复现；它与最新241架构实验使用不同服务能力，不能把两者相除申领算法收益。
- 负载为完整 Qwen2.5-3B、B1/S2 prefill、无 KV、含 embedding/36 层/LM head，8,404 个服务。只有在假设一个 tick 等于 300 MHz 一拍时，才换算为 558.03613622 s 和 0.00358399729 prefill token/s；不是校准生成速度。
- 同池贪心关键链 167,410,873,122 ticks 的 Dot/Product/Add/其他分别为 84,500,059,460 / 34,877,867,696 / 33,740,886,712 / 14,292,059,254，约 50.5% / 20.8% / 20.2% / 8.5%。它包含搬运与转换，不是纯 MAC/DDR 归因。贪心和 DP 分母相差 32,256，不混用精确分母。

上游历史收益：共同阶段后端使旧强计划下降约17.39470%，不是新搜索算法收益；S32 Add的23个FFN子服务串行成本少29.8194%，不是FFN完成时间；迭代14驻留样本的强同池贪心到最好计划仅少0.40294%复制成本。迭代15已接入覆盖前沿，但整图搜索和新驻留真实权重结果仍待终态。M侧足迹仅16–88/1024字、E侧7–12/1024字，每元素仍冷启动；应验证跨迭代有限S状态，而不是直接删LOAD或放开整S租约。

## B1 decode：精度与命令间隔改变结论

从固定Qwen配置独立计算：每层密集线性77,070,336 MAC，36层加完整词表head共 **3,085,697,024 MAC/token**。下表按3M、300MHz、完美分片/驻留供数、无其他开销计算上限。间隔来自#238/PR239，本轮未重测；候选硬件不属于已交付M。这里研究原M/PR239的数位乘法合同，不约束最新PR241另行假设的原生S32宏，两者M数量和算术能力不能混用。

| 硬件 / 操作数 | K、N | 上游驻留命令间隔 | 仅密集线性工作上限 token/s |
| --- | --- | ---: | ---: |
| 现有 M，S8×S8 | 32、8 | 16 拍 | 4.66669 |
| PR239 候选，S8×S8 | 256、8 | 44 拍 | 13.57583 |
| PR239 候选，S16×S8 或 S8×S16 | 256、8 | 108 拍 | 5.53090 |
| PR239 候选，S16×S16 | 256、8 | 300 拍 | 1.99112 |

K256 的 S8 驻留微测试约为 K32 的 2.91 倍，不是整网 2.91 倍。当前 S32×S16 配方还要更多分量，不能直接采用最宽松的 S8 上限。候选每 M 新增 7 KiB B 寄存器和 3 个输入端点，若三颗均替换需单列 21 KiB 与相应接口；尚无 LC、物理和整网资格。

这说明：仅延长 K 不能保证在既定精度下达到数 token/s；S8 或更低比特必须先有模型质量证据。保持宽格式时，应比较原生 S32 向量服务、降低分量开销或更大计算规模，不能靠改换单位达到目标。该计算是当前直接密集 M 路径的条件边界，不覆盖其他未注册快速算法。

## 载荷、容量和事务粒度

假设 B1 每个 token 对所有密集线性权重各流读一次，不计小规模常驻、对齐、元数据和重复访问：

| 权重载荷 | bytes/token | 5 token/s 所需 GB/s | 10 token/s 所需 GB/s |
| --- | ---: | ---: | ---: |
| 16 bit | 6,171,394,048 | 30.857 | 61.714 |
| 8 bit | 3,085,697,024 | 15.428 | 30.857 |
| 4 bit | 1,542,848,512 | 7.714 | 15.428 |

GB 为十进制。4 bit 只作载荷情景，当前 M 没有自动获得原生 Q4 服务或同质量资格。上述数字不是实际 DRAM 请求量或已校准带宽，更不能从 PR241 的逻辑记录/总时长倒推器件峰值。

S16 KV 在理想 GQA 跨 query-head 复用下，长度 128/512/2048 每 decode token 最少遍历约 4,718,592 / 18,874,368 / 75,497,472 bytes 的已有 K/V 载荷；追加、请求头与对齐另计。实际实现若按各 query-head 重读，可明显高于此数。S2 无 KV 图不能证明这条路径已存在。

当前冻结图有 8,249,973,644 个逻辑 128 位记录（名义 131,999,578,304 B）。标量记录只放一个 S16 时有效载荷仅 1/8，但不能据此把流量直接除八：动态 pack/unpack、地址步幅、S 容量与端口都需要真实通路。现有 P 的 pack16 只将四个 S16 放到低 64 位、上 64 位清零；它不自动把两拍拼成八个 S16，更不能直接送给任意 E/N 接口。

PR241 的 64 次单字 LOAD（64×20=1280 ticks）与一次 64 字连续 LOAD（287 ticks）仅说明孤立描述符约 4.45993 倍、少 993 ticks 的机会。只有源/目的地址连续、所有者/方向一致、没有消费者/覆盖/ACK 屏障，才能用合法多字描述符替换；不能把该倍数推广到所有服务。
