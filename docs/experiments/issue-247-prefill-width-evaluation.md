## 为什么继续扩宽收益很小

以idealdual层为例，原32B/单服务到64B/双组交错：

| 计数（百万core cycles） | 原32B单服务 | 64B双组交错 |
| --- | ---: | ---: |
| P0共享A feed阶段 | 50.102474 | 30.289568 |
| P0服务阶段 | 55.536538 | 53.648080 |
| P0输入ACK等待 | 14.306452 | 15.250506 |
| P0累计elapsed | 71.614315 | 70.669911 |
| 整图Dot阶段 | 72.102929 | 71.158525 |
| 整图总周期 | 136.397348 | 135.452944 |

A feed缩短约39.54%，但它与计算重叠。最佳配置两P服务阶段合计107,261,600 core cycles，恰好等于未改变的M_work_ticks：在该模型的max(compute,adapt,localread,feed)及原tail合同中，服务已经达到M计算成本。64→128时两P A feed合计还由60,579,136降到59,321,280 cycles，但整图速度不再变化。缩短服务后部分输入ACK等待显露出来，因此不能将各项重叠等待简单相加为可回收时间，也不能将ACK等待全归因于DDR总带宽。

非Dot阶段保持约64.2944百万core cycles（各阶段取整会有约1拍差异），约占最佳整图47.47%；本次A扩宽没有优化这些阶段。结论是：本场景32B已接近A供数收益平台，下一步应关注M计算服务、输入ACK流水及非Dot阶段，而不是继续扩大A端口。

128B消费者另受有限信用限制：每P仅4×64B FIFO，一行最早经1拍服务＋2拍返回延迟＋1拍消费后归还信用，故无排队时长期供数上界约64B/拍/P。128B同拍双行已由定向测试实际覆盖；峰值能力不等于持续带宽。8槽是解除这一单P信用限制的必要条件之一，但本轮未测试8槽，且计算成本已覆盖feed，不能推定扩FIFO会增加整图速度。

## 面积与证据边界

双组方案复用共享池8颗4KiB宏，容量仍32KiB，新增共享SRAM宏为0。双读仲裁、FIFO多项访问、M并行写入和互连增加逻辑，未综合，不能给出可信mm²增量或频率保证。
共享A同址双P读取分别计费，不含广播。双组128B是无冲突峰值，单组冲突需要排队；每P128B不意味着两P合计256B持续供数。
未完成原生S32拆分、K32实际命令、DMA桥/完整模型权重与token生成、STA/P&R或功耗；本结果不构成原生RTL实测token/s。
