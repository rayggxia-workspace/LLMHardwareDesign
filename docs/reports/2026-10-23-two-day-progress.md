## 1. 当前进展

这两天已形成“具体划分候选 → 整数数值参考 → 真实小模型验证 → 同资源端口/通信比较 → 服务器补充验证”的实验链，发现了会改变 Block 设计的实际数值和资源约束。

目前可以排除部分不合理的划分方式，并给出有证据的候选边界；**尚未完成最终划分、全整数 LLM 或端到端硬件/PPA 收益验收**。下面的“完成”指实际实验执行和材料交付；相关研究 PR 多数仍待审查、合并。

## 2. 已完成的主要工作

### 2.1 明确研究对象和具体 Block 候选

围绕共同问题开展研究：不同 LLM 的哪些计算、状态和通信应在制造前固定在 Block 内，哪些连接应留待产品确定后定制，以及真实容量、端口、布线和时序约束下能获得多少收益。

已给出六类可复用模板及计算、状态、接口、预连线和验证假设：

| 模板 | 主要职责 |
| --- | --- |
| M | 矩阵 tile、部分和与完整归约语义 |
| V | 向量、归一化、非线性和格式转换 |
| A | 注意力 score、概率及较宽输出归约 |
| R | 卷积历史和递推矩阵状态更新 |
| S | 有明确容量、bank 和端口的存储 slice |
| D | 数据搬运、依赖、同步和状态版本控制 |

这些是候选模板，并非每个模型层各制造一个独立 Block。最小实验已收敛为数值门、边界判别和冻结后的独立验证，避免盲跑所有模型、长度和精度的组合。见 [PR44：具体候选方案与最小实验](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/44)。

### 2.2 建立 W8A8/INT32 候选合同和整数验证工具

主矩阵候选以 W8A8、INT32 部分和为目标；KV、向量、概率、递推状态、scale 和宽归约分别声明格式。明确 RNE 舍入、饱和、溢出检查和重新量化边界，保留现有 FP32/BF16 证据的原始条件。

已完成：

- 20 项业务测试、1,028 项串行重新量化 RTL 用例。
- 严格采集格式、SHA-256 接收校验和独立整数重放工具。
- 4,608 个量化划分设计点的受控搜索与容量、元数据、物理传输粒度审计。

这些结果不证明参考 RTL 已支持全部候选数值能力；宽乘法、除法、开方、LUT、转换与状态更新仍需分别落实实现和成本。见 [PR34](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/34)。

### 2.3 完成 Llama-3.2-1B 的跨模型最小验证

复用已下载并校验的原始 BF16 权重，在本机完成一层完整 **4Q/1KV 共享组**，覆盖短 prefill 和 cached decode，核对实际 norm、RoPE、线性和注意力边界。

- 所选浮点完整/cached 执行通过预设一致性检查。
- 完成整数 GQA、16 个线性条件和 384 个端口/服务配置。
- 完整 K 的 43,520 个线性输出通过独立 INT64/Fraction 检查。
- 发现每个 K128 部分和提前重新量化再求和，会改变 **28,950/43,520** 个输出，不能拿这种不同数值语义的算法比较划分收益。

这证明小模型间可以复用明确合同和工具，也暴露了不能直接沿用统一静态 scale 的问题。见 [PR57](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/57)。

### 2.4 重点完成 Llama down_proj 校准和 scale 粒度研究

本机完成 **24 个候选、144 个数值条件、1,152 个服务配置**，正式数值与服务均重复执行，保留全部失败和原始记录。范围为 layer0 down_proj、完整 K8192、前 16 个输出通道。

| 方案 | 六个局部条件中的最坏输出相对 RMSE |
| --- | ---: |
| 静态全 K 激活 scale，原/扩展校准、max/MSE | 91.83% |
| 动态逐行激活 scale，权重每输出 scale | 16.88% |
| 动态激活 K128，权重每输出 scale | 7.36% |
| 动态激活 K128，权重每输出 K128 | **5.39%** |

关键发现：

1. 扩充校准文本及输入 MSE 搜索没有解决本轮静态全 K scale 过粗的问题；scale 粒度比单纯增加校准量更关键。
2. 最好候选仍未通过事前冻结的 **5% 局部探索门**。这不是完整模型质量验收，也不能事后调门槛宣布通过。
3. 最好候选的 heldout prefill 误差在最终重新量化前为 4.81%，之后为 5.39%，输出格式/scale 成为后续有区分度的小实验。
4. 分组 scale 改变后，必须显式处理“部分和 → scale 对齐 → 完整归约 → 一次最终 RQ”。
5. 粗格式界可能需要 35 位，但结合当前实际权重和所见 scale，所测 16 个输出的更紧界可放入 INT32；**既不能据粗界宣布必须 INT64，也不能据当前切片宣布全层永远 INT32 安全**。若使用范围守卫，其元数据和在线成本须计入。

见 [PR60：完整实验、决策和可重放证据](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/60)。

### 2.5 完成同资源 RQ 位置和端口比较

已有 Qwen 小切片的 E2a 完成 384 个受控组织及服务器独立重放；计入 bank 单口约束、私有缓冲、包头、对齐、分片、同步和调度。

两侧分别选择已有策略中的最好配置后，近矩阵单元 RQ 的模型服务收益最大约 **0.57%**。Llama down_proj 的所选代表条件约为 **1.4%/2.3%**。这些均是特定有界服务模型的结果，矩阵/消费者等仍未完整 RTL 校准，不能当作实测芯片加速。

明确发现：**减少边界字节不一定改善关键路径**；decode 小包可能因包头和对齐而完全不减少实际链路占用。目前不足以把近端 RQ 固定为不可绕过的唯一通路。见 [PR52](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/52)、[PR60](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/60)。

### 3.1 新跨模型结果：down_proj改善，但不等于全模型通过

所选层、完整K/前16输出，prefill/decode最坏输出relativeRMSE：

| 模型/层 | 静态全K激活scale | 动态行scale/Wout | 动态K128/Wout | 动态K128/W128 |
| --- | ---: | ---: | ---: | ---: |
| Gemma local layer0 | 28.40% | 14.03% | 4.08% | **3.81%** |
| Gemma global layer5 | 21.22% | 18.23% | 4.21% | **4.00%** |
| Qwen2.5 layer0 | 27.45% | 18.27% | 3.48% | **3.37%** |
| Qwen3.5 layer3 | 8.58% | 5.32% | 4.93% | **4.83%** |

动态激活K组scale的作用跨模型重现；Wout在这些切片已接近W128，不能一律加细权重metadata。Gemma部分q/o投影仍出现输出饱和，原Llama5.39%失败保留。5%只是局部探索门，不是完整语言/数学/代码质量验收。

### 3.2 注意力应把概率精度与KV精度分开

所选完整GQA组最坏输出relativeRMSE，有显式FP64 softmax回退：

| 模型/组 | KV8/P8 | KV8/P16 | KV16/P16 |
| --- | ---: | ---: | ---: |
| Gemma local | 34.47% | 3.52% | 0.50% |
| Gemma global | 6.89% | 4.49% | 1.74% |
| Qwen2.5 | 13.98% | 12.50% | 0.58% |
| Qwen3.5 global | 23.37% | 2.88% | 0.95% |

P8/P16表示非负P7/P15有效分数码，存储I8/I16。不能制造前把全部路径统一压到KV8/P8。若只给S8乘法器，16×16需9个limb乘积及移位相加，不是免费INT16能力。

### 3.3 重要新结果：有条件的INT32，而非盲目加宽

粗格式上界可到44位，但归一化概率和、固定V scale、有效长度和范围守卫能明显收紧。本轮**90046**实际执行56条件、**1474560个完整PV I32输出**，全部匹配I64参考。它需要每活动query/head的4B Psum守卫及固定单位；不覆盖未归一化online attention、更长任意上下文或跨页单位变化。整数exp/div仍未实现，不能称全整数attention。

三个主测所见固定W/scale的线性充分界也可在32位内，但只覆盖所测16输出/所见scale；L1证书表和在线检查成本必须计入。相比“哪个算子应该合成一块”，更有用的边界依据是**哪些计算必须一起维护单位、范围和状态不变量**。

### 3.4 容量/通信发现与可复查交付

Gemma4096+32的原生FP32 KV逻辑量约393MiB，full prefill底层分配约1096.5MiB，cached结束约393.25MiB：窗口正确不等于底层没有保留大base对象。容量划分要区分活跃窗口、物理对象生存期、prefill工作区和硬件ring实现。

90047重新按逐token核算420条件的包；Gemma一个32步decode/16输出例子中，最终I8实际包4096B，不能用聚合640B代替。部分和、scale元数据、静态驻留、16KiB源暂存、guard及宽路径分别记账。它仍是字节/服务下界，不是新模型芯片加速比。

主数据包569140969B及Phi封存包30232659B保存在已授权服务器，完整SHA索引在PR62。仓库7.27MB精选包可离线重放4个GQA/6个整数case；全420条件的完整浮点/编码数据读取服务器主包。两个真实“改数据后重写SHA”的负例均被独立数值/来源检查拒绝。管理结构、五套项目业务及17项新边界测试通过。

见 [PR62：报告、数据索引、源码与交接](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/62)、[PR36：原GPU证据](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/36)。

## 4. 目前对划分方案的启发

- 制造前应优先保留局部完整归约、必要的宽中间值、局部状态反馈及严格完成/版本语义；提前 RQ 不能改变数学函数。
- scale、bias、重定标、宽归约和格式转换必须作为计算图节点与接口信息，不能视为免费操作。
- INT32 部分和留在 M 内是有条件的候选：乘积单位相同才可直接求和，混合 scale 需要对齐和范围验证。
- 近端 RQ、共享 V 和较宽旁路继续保留；根据精度、端口争用、批量和实际通信粒度选择，尚不冻结唯一连接。
- 普通 GQA、局部/全局注意力、混合递推状态应分别验证，不能把 BF16/FP32 字节统一除以四当成 INT8 容量和收益。

本轮四模型CPU批次按既定范围已执行并归档，以下是下一阶段研究，不把它们混称本批已完成：

3. 复用实际连续递推状态，做同资源局部R/共享V对照，计backing和其他请求争用；不重复长模型推理。
