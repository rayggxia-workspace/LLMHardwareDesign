# 面向不同 LLM 架构的预制计算底座：原语粒度、算子感知、预互联与复用

> **讨论整理｜2026-10-19**  
> **定位：** 将原始研究问题和对应分析整合为一份连续的架构研究笔记。保留数值案例、公式、设计权衡和后续实验思路；仅重组章节，减少多级编号。  
> **讨论边界：** 目标是“预制计算底座 + 有限顶层金属／通孔后期定制”，而非固定模型权重 ROM，也不预设每一种神经网络算子都对应一个独立的物理 Block。

## 原始研究问题

> 我现在对这句话特别有感触。我觉得我们的 Block 如果单纯以某个神经网络算子为粒度可能太粗，灵活性不够；应该往下去找一些计算／操作的原语，去组合出不同架构对应的算子（当然如果有些功能比较固定，可能可以粒度稍微大一些）。
>
> 不过另一方面，底层的 Block 可能还需要有更上层算子感知的信息。就比如我们之前提到 GQA：假如考虑 KV 和 Attention 单元之间的互联是底层做好的，就需要底层感知多个 Q 头共享一组 KV 这种结构；如果互联是顶层定义（假设顶层资源足够），那么也需要预定的 Block 中 Attention 单元可以多一些，而且可以并行。
>
> 而且，虽然我们拆分了底层原语，但是如果不进行一些预互联，就会把布线压力都给到后续的上层工作（除非排布对上层资源有利，不会用到上层中的长线）。这也是需要平衡的一步。
>
> 所以，我觉得我们可能需要继续分析更多不同的 LLM 架构案例，就像刚刚对比 GQA → DeltaNet → MoE 一样（Mamba 可能差异有点大了），然后针对这些不同分析上述问题，已经对比过的也需要重新分析。
>
> 另一点是：当讨论完这些算子的异同后，还需要考虑某些计算原语会在不同算子中复用。这是否适合“预制底座 + 顶层互联”？会不会虽然 Block 拆分是计算原语级别，但复用只能发生在算子级别而不是算子内部？这一点需要辩证分析。

**核心研究问题可以归纳为：**

- **抽象粒度：** 计算能力应拆到多细，哪些稳定组合又值得保留为较大结构？
- **上层感知：** 底层应预先支持哪些共享、归约、反馈、动态寻址关系，而不必固化模型名字？
- **物理分界：** 哪些连接必须在预制底层完成，哪些留给后期少量金属定制？
- **复用边界：** 原语是否能够在同一算子内部和不同算子之间时分复用？代价是什么？
- **验证路径：** 如何用不同 LLM 架构的真实数据流，而不是只用抽象算子图，比较不同底座方案？

## 一、总体判断：原语化、算子感知与物理局部性并不矛盾

**建议的方向是：计算能力按原语组织，物理结构按局部数据复用组织，顶层互联负责组合这些局部结构。**

但要避免两个误区。

**误区 A：“计算原语更细”意味着每个原语都必须是独立的物理 Block。**

点积、外积、逐元素乘加、归约可以在逻辑层独立描述，但在物理层可能更适合共享局部 SRAM、累加器、寄存器和短反馈路径。如果每个原语都靠后期顶层走线连接，可能把原本局部的数据循环变成巨大的跨块通信开销。

**误区 B：算子感知就等于把完整算子硬编码到底层。**

底层未必需要知道“现在是 Qwen 的第七层 GQA”。更有价值的是支持可以在多个模型中复用的执行关系，例如“多个查询上下文读取同一块数据”“状态需要读—改—写”“某次计算使用运行时选出的权重地址”。

### 模型特征应转换为什么硬件信息？

| 上层模型特征 | 底层真正需要支持或接收的信息 |
|---|---|
| GQA：多个 Q 头共享一组 KV | 多个消费者共享一份输入；数据驻留时间；累加上下文数量 |
| DeltaNet：递推更新状态 | 状态的读改写依赖；何时覆盖旧值；写回路径 |
| MoE：动态选择专家 | 运行时任务编号、地址、缓存命中状态、完成标志 |
| Softmax、归一化 | 归约范围与数值精度；何时统计完成；是否需要回放 |
| 不同量化格式 | 权重／激活位宽；缩放因子范围；累加与舍入位置 |
| 分块矩阵运算 | 分块尺寸、步长、尾块长度、部分和归属 |
| 稀疏注意力 | 索引列表、分散读取、返回结果与任务的对应关系 |

因此，**原语化回答“硬件可以组合出什么”，算子感知回答“怎样组合才能保持数据局部、复用有效且满足数值语义”。**

还需要注意：GQA、MoE、滑动窗口和门控 FFN 可以同时存在于一个模型中。因此，我们提取的是**可组合的数据流特征**，而不是为每种模型定制一套互不兼容的硬件。

## 二、跨 LLM 架构的案例：从模型特征推导计算、存储与互联需求

### GQA：KV 共享既可以是空间广播，也可以是时间复用

分组查询注意力（Grouped-Query Attention，GQA）的特征是：**多个查询头共享同一组 K/V**。与普通多头注意力（Multi-Head Attention，MHA）相比，它减少 KV 存储副本，但每个 Q 头仍要计算自己的分数和输出。

假设四个 Q 头共享一组 KV，有两种实现。

**空间并行：**

```text
                    ┌─→ Q0 计算单元
KV 本地缓冲 ─────────┼─→ Q1 计算单元
                    ├─→ Q2 计算单元
                    └─→ Q3 计算单元
```

四个计算单元同时消费相同 KV。优点是降低查询延迟；代价是更高的输出扇出、局部带宽和算术面积。

**时间复用：**

```text
KV 本地缓冲 → 同一个计算单元，依次处理 Q0、Q1、Q2、Q3
```

关键的调度不一定是“算完 Q0 的全部历史，再开始 Q1”，而可以按 KV 分块组织：

```text
载入 KV 分块 0 → 用 Q0/Q1/Q2/Q3 消费 → 替换 KV 分块
载入 KV 分块 1 → 用 Q0/Q1/Q2/Q3 消费 → 替换 KV 分块
……
```

四个 Q 头分别保留其输出累加值和在线 Softmax 统计量（如局部最大值、归一化分母）。因此时间复用也能把同一 KV 分块的外部读取成本分摊给多个查询头，尽管总算术工作没有消失。

**严格容量算例。** 假设 KV 分块为 64 个历史词元、头维度 128，K/V 均为 16 位：

\[
M_{KV}=2\times64\times128\times2=\boxed{32\ \mathrm{KiB}}.
\]

若四个查询头的输出使用 FP32 累加，需要：

\[
M_{O}=4\times128\times4=\boxed{2\ \mathrm{KiB}},
\]

另加少量 Softmax 统计寄存器。由此可见，**通过本地 KV 缓存和多组计算上下文，单套计算单元也能利用 GQA 的共享特性**。

**对底座的要求：** 预制“可共享读取的本地缓存 + 多组累加上下文 + 可选局部广播／时间复用”，而非唯一固定“四个 Attention 单元连一个 KV Bank”。多个并行单元是否值得配置，取决于延迟目标、供数带宽和面积。

### DeltaNet：原语可以拆，但状态更新闭环应该尽可能局部

DeltaNet 的核心是**固定大小状态矩阵的读取和递推更新**，而非扫描全部历史 KV。为表达数据流，令状态以转置形式存储为 \(R=S^T\)，可简写为：

\[
u=Rk,
\qquad
\delta=\beta(v-\alpha u),
\]

\[
R'=\alpha R+\delta k^T,
\qquad
o=R'q.
\]

这里省略了输入归一化、门控系数的生成和实际定点运算细节。数学层面的原语链是：

```text
点积 → 向量乘减 → 外积更新 → 点积
```

如果这几个操作被放在相距很远的独立物理 Block，整个状态或大量中间值可能多次跨块移动。

**严格容量算例。** 若状态维度 \(128\times128\)，每元素 16 位：

\[
M_S=128\times128\times2=\boxed{32\ \mathrm{KiB}}.
\]

按行计算时，每行状态只有：

\[
M_{S_i}=128\times2=\boxed{256\ \mathrm{B}}.
\]

第 \(i\) 行能够按下面的依赖关系处理：

\[
u_i=R_i k,
\quad
\delta_i=\beta(v_i-\alpha u_i),
\quad
R'_i=\alpha R_i+\delta_i k^T,
\quad
o_i=R'_i q.
\]

于是可以考虑把一行读取、两次点积、更新与写回尽量留在同一个局部计算—存储簇内：

```text
状态 SRAM → 行缓冲 → 点积／更新 → 同一行缓冲 → 状态 SRAM
```

这并不是否定原语划分，而是说明**逻辑原语可以独立，物理数据反馈应尽量短**。它还要求行级处理遵守真实的数值与读写依赖。

现有实现提供了两种边界参考：

- **fable5_llm** 的 `dn_step`：使用专用、分阶段的状态更新流水线与状态存储接口。
- **openTPU**：既可以把 DeltaNet 映射为 `RDOT`、`MUL`、`SUB`、`OUTER` 等原语，也设计了流式融合路径 `DSTEP`，让状态数据直接通过计算数据通路、减少通用暂存区往返。

两套实现的位宽、数值规则和硬件平台不同，不能仅凭结构名称推断 PPA 优劣。

**对底座的要求：** 不必固定完整 DeltaNet 黑盒，但值得研究“状态缓冲—点积—向量更新—写回”这种可复用的局部闭环。

### MLA：缓存压缩和计算维度并不是一回事

多头潜在注意力（Multi-Head Latent Attention，MLA）与 GQA 都试图减少 KV 相关存储，但机制不同：GQA 减少独立 KV 头，MLA 保存压缩后的潜在表示。以下只分析不含位置编码的内容分支。

设缓存中存储潜在向量 \(c_t\)：

\[
k_{t,h}=W_{K,h}c_t,
\qquad
v_{t,h}=W_{V,h}c_t.
\]

通过改变乘法次序，可以避免逐个历史词元重建完整 K/V：

\[
q_h^T k_{t,h}
=(W_{K,h}^Tq_h)^Tc_t,
\]

\[
\sum_t p_{h,t}v_{t,h}
=W_{V,h}\left(\sum_t p_{h,t}c_t\right).
\]

**严格容量算例。** 采用 DeepSeek-V3 的有关配置：内容潜在维度 512、独立的位置编码维度 64，缓存均按 2 字节／元素估算，则每词元、每层压缩缓存主体为：

\[
(512+64)\times2=1152\ \mathrm{B}.
\]

64 个词元分块占：

\[
64\times1152=\boxed{72\ \mathrm{KiB}}.
\]

**关键区别：缓存变小，不意味着计算接口就一定可以固定在传统 128 维头宽度。** 内容点积可能在 512 维潜在空间进行，输出先在潜在空间累加，再投影回值空间。

**对底座的要求：** 支持不同的点积长度／输出累加长度、潜在缓存共享、前后投影与 Attention 的局部连接，以及位置分支与内容分支的合并。不宜预制唯一的“128 维注意力头”接口。

### 滑动窗口与跨层 KV 共享：运算不变，存储生命周期改变

**滑动窗口注意力（Sliding-Window Attention）** 主要改变可访问的历史范围，不一定改变点积、Softmax 和加权累加。以 Gemma 3 的局部窗口为 1024 的机制作为比较对象，设总上下文为 32768：

\[
32768/1024=\boxed{32}.
\]

在其他条件相同时，局部窗口需要保留的历史位置数量仅为全局注意力的 \(1/32\)。此时更直接的硬件需求是循环地址、有效窗口控制，以及**按层分配不同容量的 KV 存储**。

若每个算子 Block 都固定携带同等大小的 SRAM，可能出现局部层存储浪费、全局层又不够用的矛盾。因此应比较“计算单元绑定大 KV Bank”和“计算单元绑定小本地缓冲、外部大存储共享”两种结构。

**跨层 KV 共享（Cross-Layer Attention，CLA）** 是不同层使用同一组 K/V。与 GQA 在查询头之间共享不同，它在模型层之间共享：

```text
同一计算簇分时处理：
KV Bank → 层 L → 保留 KV → 层 L+1

空间展开的两个计算簇：
                    ┌→ 层 L 的簇
共享 KV Bank ───────┤
                    └→ 层 L+1 的簇
```

前者主要增加数据生命周期管理，后者还可能带来跨簇扇出与长线。

**对底座的要求：** 让“某份数据被哪些计算阶段使用、持续到何时”参与存储分配和布局。模型减少缓存副本，并不自动意味着物理互联成本也下降。

### MoE：先判断移动权重还是移动激活

混合专家（Mixture of Experts，MoE）仍大量使用矩阵与向量原语，但哪个专家执行取决于运行时的路由结果。

以 Qwen3.5-35B-A3B 的典型配置为例：每层 256 个路由专家、每词元选择 8 个；隐藏维度 \(H=2048\)，单个专家的中间维度 \(F=512\)。

单个门控 FFN 专家的主要三个矩阵共：

\[
3HF=3\times2048\times512=3{,}145{,}728
\]

个权重。只按 INT4 权重本体、不含缩放元数据：

\[
3{,}145{,}728\times4/8
=\boxed{1.5\ \mathrm{MiB/专家}}.
\]

而 2048 维、16 位的输入向量只有：

\[
2048\times2=\boxed{4\ \mathrm{KiB}}.
\]

由此出现两种物理拓扑：

```text
方案 A：共享计算，移动权重
专家权重池 → 动态地址／流式读取 → 少量共享计算簇

方案 B：权重近计算，移动激活
当前激活 → 动态分发 → 驻留专家权重的计算簇 → 结果聚合
```

方案 B 在权重确实驻留时可能显著减少跨远距离传送的数据量，但需要分布式大容量存储，也面临专家负载不均。权重池放不下时，不能仅靠改变互联解决容量问题。

MoE 的控制流程还需要运行时专家索引、缓存目录、命中／未命中处理、动态地址、等待、输出聚合。**这些控制能力并不要求复制 256 套 FFN 电路**；共享 MAC 可以分时执行被选中的专家。openTPU 即用矩阵引擎、最大值搜索、循环和等待机制构成这套流程。

**对底座的要求：** 先决定权重驻留与缓存层级，再决定任务分发、激活广播和计算簇数量；不应先随意摆放 MAC，再把所有专家访问问题交给后期金属。

### 动态稀疏注意力：少算不一定少通信

与地址规则的滑动窗口不同，动态稀疏注意力先根据输入选择历史位置，再读取被选中的 KV 分块。例如从 4096 个历史位置中选取：

\[
[7,33,801,2050,\ldots].
\]

这些地址不一定连续，硬件可能需要索引队列、Bank 冲突处理、多个未完成访存请求，以及读取结果与原查询的对应关系。

稀疏注意力与 MoE 都存在“打分／选择／索引访问／结果重排”，但两者的访问尺度不同：

| 对比 | MoE | 动态稀疏注意力 |
|---|---|---|
| 被选对象 | 专家计算任务或权重 | 历史 KV 位置／分块 |
| 单个对象尺寸 | 可能达到 MiB | 通常小得多 |
| 主要瓶颈 | 驻留率、权重迁移、任务分配 | 细粒度访存、Bank 冲突、返回重排 |
| 可能共享的基础能力 | 索引、地址生成、队列、完成标志 | 索引、地址生成、队列、完成标志 |

因此适合提取的共同原语是**索引驱动的数据访问**，不是固定缓冲尺寸的“万能专家／稀疏路由 Block”。

### 门控 FFN、Softmax 和归一化：可融合性受到数据依赖与数值边界限制

以 SwiGLU 型 FFN 为例：

\[
g=W_gx,
\quad u=W_ux,
\quad z=\operatorname{SiLU}(g)\odot u,
\quad y=W_dz.
\]

数据流为：

```text
             ┌→ Gate 投影 → SiLU ─┐
输入 x ──────┤                   × → Down 投影
             └→ Up 投影 ─────────┘
```

如果同一矩阵簇承担三次投影，就必须支持：

```text
矩阵引擎 ↔ 本地缓冲 ↔ 向量引擎
     ↑                        │
     └──────── 反馈 ──────────┘
```

仅有单向“矩阵输出→向量单元”连接，不足以让 Down 投影复用原来的矩阵引擎。

**严格容量算例。** 假设中间维度 12288，Gate、Up 输出都是 16 位：

\[
M_{g,u}=2\times12288\times2
=\boxed{48\ \mathrm{KiB}}.
\]

如果按 256 个中间元素为一块，并尽早完成局部门控，则当前块的 Gate、Up 数据本体是：

\[
2\times256\times2=\boxed{1\ \mathrm{KiB}}.
\]

这并不包含输入缓冲、Down 部分和及流水资源。它说明有机会减少中间张量驻留，却**不能保证总存储仅需 1 KiB**。

还要考虑数值语义：如果 Down 输入的量化缩放因子依赖整个 \(z\) 向量的最大绝对值，第一块 \(z\) 生成时，缩放因子尚未确定；若坚持原数值规则，就可能需要整向量保存、回放或重算。RMSNorm 等也需先完成规定范围内的统计，不能任意截断归约范围。

**对底座的要求：** 同时支持分叉汇合、局部反馈、归约上下文，以及必要的全局统计／回放路径；编译器必须显式保留“哪些元素属于同一归约或量化范围”。

### 案例汇总：从算子名字提取硬件需要的关系

| 案例 | 关键关系 | 优先评估的预制能力 | 可能留给后期定制的内容 |
|---|---|---|---|
| GQA | 多消费者共享 KV | 本地共享缓存、多组累加上下文 | 并行计算簇数量、跨簇共享范围 |
| DeltaNet | 状态读改写闭环 | 行缓冲、局部点积／更新／反馈 | 状态所属簇、簇间分配 |
| MLA | 潜在表示共享、维度改变 | 可变维度分块、投影与局部累加 | 潜在缓存与计算簇连接 |
| 滑动窗口 | 规则、有限历史 | 循环寻址、可分配缓存 | 每层存储配额和映射 |
| 跨层 KV 共享 | 生命周期跨层 | 共享存储、保持与有效标记 | 跨层消费者的拓扑 |
| MoE | 动态任务、专家驻留 | 索引、DMA、任务队列、完成标志 | 专家缓存与计算簇的映射 |
| 动态稀疏注意力 | 索引驱动的分散读取 | 收集／重排、Bank 仲裁 | 分块访问网络和局部性 |
| 门控 FFN／归一化 | 分叉汇合、归约边界 | 本地反馈、上下文、统计与回放 | 簇间通路及资源分配 |

## 三、从逻辑原语到物理 Block：预制什么，后期连接什么？

### 原语“能力目录”不是物理宏目录

| 原语能力 | 可能复用的操作 | 值得就近放置的资源 |
|---|---|---|
| 分块乘加、点积 | 投影、注意力、MLA、专家 FFN | 输入缓存、局部累加器 |
| 向量乘加、广播、外积 | DeltaNet、门控、残差 | 行缓冲、状态反馈路径 |
| 求和、最大值、平方和 | Softmax、归一化、量化统计 | 多组归约上下文、小缓存 |
| 指数、倒数、平方根倒数 | Softmax、门控、归一化 | 可复用的函数流水线 |
| 索引、循环寻址、数据重排 | MoE、稀疏注意力、滑动 KV、MLA | 地址生成器、队列、Bank 选择 |
| 同步、保持、写回 | 所有分块及状态型计算 | 控制器、有效标记、上下文表 |

这些是逻辑上需要覆盖的功能。**不应据此直接画出六个必须通过顶层金属互联的孤立宏。** 特别是计算位宽和数值规则不同的乘法器，不能因为同叫“乘法”就认定可以无代价互换。低精度权重乘法、Q/K 点积和状态更新在输入位宽、累加精度、吞吐和端口要求上可能不同。

### 候选物理组织：局部计算—存储簇

```text
                     一个预制计算—存储簇
┌─────────────────────────────────────────────┐
│  分块乘加 / 点积                             │
│           ↕                                  │
│  本地 SRAM + 累加器 + 多组计算上下文         │
│           ↕                                  │
│  向量更新 / 归约 / 必要的非线性函数           │
│                                             │
│  局部选择器 + 反馈路径 + 地址生成 + 控制      │
└─────────────────────────────────────────────┘
                 ↕ 标准化对外接口
             后期定制的簇间互联
```

上图是**候选结构**，不是要求每个簇都拥有完整的算术功能。可以比较偏矩阵、偏向量／状态、偏存储的几类簇；局部高复用资源就近放置，低频组合关系留到更高层。

### 为什么不宜把所有原语连接都放到顶层？

假设状态更新时并行处理 128 个 16 位元素，单向数据宽度是：

\[
128\times16=\boxed{2048\ \mathrm{bit}}.
\]

如果后期跨簇接口只有 256 bit、同一时钟频率，那么传输完整一行至少需要：

\[
2048/256=\boxed{8\ \text{个传输周期}}.
\]

这**不意味着整个算子必然慢 8 倍**；它给出的是这一数据传输的带宽下界。即使线很短，2048 位并行接口仍可能引起金属资源、驱动负载和功耗问题。

因此衡量连接成本不能只看长度，还要看：

- 每次需要跨越边界的数据量与接口位宽；
- 峰值同时传输的通路数；
- 数据是否能被局部缓存截留；
- 是否每周期需要宽反馈；
- 不同任务是否争用相同通路。

**优先考虑预制的连接：** 状态反馈、部分和本地累加、局部广播、归约结果回送、计算与本地 SRAM 之间的宽路径。

**优先考虑留给后期的配置：** 簇间组合关系、存储归属、簇间带宽分配、共享数据跨簇分发范围。

这只是待验证的初步分界，不能预设所有跨簇数据量都低。

### 预制轨道与后期定制并用

一种折中结构是：

- 簇内部主要连接固定；
- 簇间预制有限数量的干线、缓冲器／寄存器位置和标准化连接端点；
- 后期少量金属／通孔决定哪些端点接入哪些轨道，以及哪些簇相互连接。

这避免了两种极端：既不是 FPGA 式任意可编程开关网络，也不是“后期从零承担全部高速数据线”。

**物理限制必须单独处理：** 在仅定制最顶层或少量后加工金属、连接分辨率为微米级的设想下，底层没有预留的驱动器、时钟、存储端口、可达引脚和中继资源，后期无法凭空生成。顶层面积足够也不等于驱动、时序与供电自动成立。

## 四、原语能否在算子内复用？如何验证哪种划分更好？

### 先把三种“复用”分开

| 复用类型 | 含义 |
|---|---|
| 跨定制版本复用 | 相同预制计算簇，通过不同后期连接服务不同模型或产品版本 |
| 运行时计算复用 | 同一套电路在不同周期承担不同计算任务 |
| 数据复用 | 同一份数据驻留在局部存储中，被多个计算任务消费 |

它们可以叠加，但不等价。特别是“后期金属固定”只表示物理连接在运行中不改变，**不表示已有连接不能承载不同时间的不同数据**。

### 算子内复用是可行的：以 FFN 为例

如果预制簇已经具有：

```text
矩阵引擎 ↔ 本地 SRAM ↔ 向量引擎
```

以及能够切换输入来源、保存中间值的地址和控制机制，那么同一个矩阵引擎可以按顺序执行：

| 阶段 | 同一矩阵引擎的用途 |
|---|---|
| A | Gate 投影 |
| B | Up 投影 |
| C | 等待向量单元完成 SiLU 与逐元素乘法 |
| D | Down 投影 |

这就是**同一个 FFN 算子内部的计算复用**，完全不要求每个阶段重新修改金属连接。改变的是输入地址、控制信号与数据内容。

类似地，GQA 的多个 Q 头可以在同一个点积单元上分时执行；DeltaNet 的旧状态点积和新状态点积也可以复用算术路径。

### 什么情况下你的担心成立？

若预制的物理连接只有：

```text
矩阵引擎 → 向量引擎 → 输出端口
```

既没有返回矩阵引擎的路径，也没有能被两者访问的缓冲，那么执行“矩阵→向量→同一个矩阵”会受限。不得不复制矩阵单元、绕到远端存储，或者修改既有连接。

因此真正的条件是：

> **一个算子各阶段需要的连接之并集，能否由预制簇内部已有的路径和有限的运行时选择机制覆盖。**

这里不一定需要全连接。针对有限的数据流形态，少量本地选择器和反馈路径可能足够。

### 算子间复用不一定比算子内复用便宜

同一个算子内部的中间值通常具有明确的生命周期和较强局部性；跨算子共用远端资源，可能引入额外数据往返、暂存、竞争和上下文切换，还可能破坏原本可以重叠的流水阶段。

因此不要预设“算子内不适合复用、算子间更适合”，应该比较实际的数据量与并发关系。

同样，**能复用并不意味着应该全复用**。一个简化吞吐算例：两个流水阶段分别独占一种运算资源 8 周期。若各有独立硬件，理想平衡流水线可每 8 周期接受一个新任务；若合并为一套硬件，一个任务共占用它 16 周期，那么由这套硬件施加的吞吐下界变成每 16 周期一个任务。

上述计算只展示资源占用与流水重叠的关系，不代表特定 LLM 算子的实测性能。实际还要计入缓冲、切换、访存与不均衡。

**判断原则：** 优先复用依赖明确、数据局部、上下文较小的计算；对必须并行、切换成本高、或者形成主要吞吐瓶颈的能力，考虑局部复制或更粗粒度的固定功能。

### 下一步实验：三类底座，在同一组案例下比较

| 方案 | 结构假设 | 希望验证什么 |
|---|---|---|
| **A：完整算子块** | QKV、FFN、Attention 等作为较大物理块 | 局部效率是否足以抵消跨模型灵活性不足 |
| **B：孤立原语块** | 原语独立，主要靠后期互联连接 | 灵活性提高的同时，通信／布线代价有多大 |
| **C：原语簇 + 预互联** | 原语共享局部 SRAM、反馈与部分固定路径；簇间后期定制 | 能否获得较好的跨模型覆盖与物理效率平衡 |

同一基准下应固定工艺、算术精度、存储宏模型、工作负载与目标吞吐／延迟，再改变 Block 粒度、预连线比例与资源数量。特别要分别测量**单词元解码（Decode）**和**预填充（Prefill）**：二者的矩阵形状、权重复用和计算并行性可能不同。

#### 建议逐条统计的数据流

```text
KV → 点积
状态 → 更新 → 状态
分数 → Softmax → 加权累加
Gate / Up → 门控 → Down
专家权重 → 矩阵计算
动态索引 → 访存 → 返回与重排
```

每条边至少记录以下属性：

| 属性 | 目的 |
|---|---|
| 数据量（字节／任务、字节／词元） | 评估总通信成本 |
| 峰值与平均所需带宽 | 评估接口和金属资源需求 |
| 生产者—消费者之间的生命周期 | 判断能否局部驻留、何时可覆盖 |
| 是否存在归约或反馈依赖 | 决定是否需要额外缓冲与回路 |
| 是否可多消费者共享 | 判断本地广播／复制／时间复用 |
| 量化与舍入边界 | 保证数值等价，避免错误融合 |
| 预制层／后期层的实际走线 | 量化定制资源的消耗与时序代价 |
| 竞争、等待与流水气泡 | 判断复用是否破坏并行性 |

在物理层还需要比较：面积、标准单元和 SRAM 占比、利用率、关键路径、实际布线长度、拥塞、所用金属层及线宽／通道占用、功耗，以及后期定制层所承担的引脚数和通道压力。仅靠算子覆盖率无法判断方案优劣。

### 预期得到的结果

这项研究最终不应只回答“做几个矩阵 Block”，而应回答：

1. 哪些**算术原语组合**能覆盖目标 LLM 家族？
2. 哪些**高频局部数据流**应当在预制阶段就近连接？
3. 哪些**模型变化**可由后期金属配置、地址与指令程序吸收？
4. 哪些资源的**算子内／跨算子复用**值得保留，哪些应复制以满足并发和吞吐？
5. 相比完整算子硬化和细粒度通用互联，局部原语簇在物理实现上有什么可验证的收益与限制？

---

## 结论

目前最有价值的方向不是单纯把 LLM 算子拆得更细，而是：

> **寻找能覆盖多类 LLM 数据流的局部计算—存储结构，并联合优化原语粒度、预互联方式与运行时复用。**

可以把设计原则概括为：

\[
\boxed{
\text{算术原语尽量可复用}
\; + \;
\text{高频数据交换尽量局部化}
\; + \;
\text{模型差异尽量由后期连接与程序吸收}
}
\]

但三者存在约束，不是越极端越好：原语过细会增加互联与控制开销；预互联过多会牺牲跨模型可配置性；共享过度会抑制流水并发。

**因此，算子感知与原语化并不矛盾：原语化决定能组合什么，算子感知决定怎样组合才不会在存储、布线、延迟和功耗上付出过高代价。**
