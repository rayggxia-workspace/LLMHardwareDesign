# 第6步：取消、故障与协调复位恢复

Issue179 / PR180，Melodydt。`recovery_boot_top`保持既有主机端口和v2/64 bit执行ISA，在U/F/C/J→P四种同域变体之外增加独立恢复监督层。MC/LC、公共PM/装载管理器及Block数据通路不变；新增的是排空适配器、带取消确认的链路与恢复/结果寄存器。

## 排空后复位

监督层状态为NORMAL→DRAIN→RESET→WAIT_READY→FAILED；无法排空则进入QUARANTINE。停止新原生服务时，已经接受的原生命令继续执行，实际响应会被接收和计数；已保持但尚未驱动宏的服务以取消状态退役。源/目的单端复位请求均提升为整个组的协调恢复，不直接复位单个端点。

源S读请求若已发出，保持到接受并收到实际响应；数据尚未交给链路时可以明确取消并丢弃。链路已保存字但未向目的发出请求时，返回带原身份的负向取消确认。目的请求一旦offered便不可撤销，必须保持请求并等待真实P写入响应；源随后才能依据提交资格和匹配身份释放。已写入的数据不回滚。J未消费输出在取消路径明确排空，不能当作正常成功ACK。

只有原生服务、运输、预约、J输出和链路义务全部排空，且没有内层主机回复在途，才复位MC、双LC、三个PM协议接口、原生组接口、链路与FIFO。监督层及外层主机/失败结果寄存器不受该软复位影响。PM读取与取指的双方属于同一复位组；运行期间没有配置写，复位撤销整个程序部署。S/PM数组内容可保留，但不保留旧任务有效性，应用必须重装镜像、初始化所需数据。

排空等待1024拍仍有义务时，返回隔离结果并持续禁止新START/装载/数据访问。超时不伪造完成、提交或信用，不强制复位仍活动的服务。底层恢复响应后，可显式重试排空；安全复位后重新装载。外部物理复位是紧急边界，可能使未确认写入的落存状态未知，需整组重装及重建数据，不能解释为回滚成功。

## 管理命令15

命令15属于独立4 bit主机管理口，执行指令仍64 bit。target=3、address=0；data[7:0]子命令，[15:8]请求mask，[47:16]job，[79:48]epoch，[111:80]START序号，[143:112]generation，[255:144]保留0。

| 子命令 | 行为与字段 |
| --- | --- |
| 0 CANCEL | 仅活动且尚未拥有终态的作业；mask=0，四项身份必须匹配当前START。接受回复仅表示请求已受理，随后从RESULT读取消终态。 |
| 1 REQUEST_RESET | mask=1源、2目的、3整个组，均执行整组排空/复位。运行时校验完整身份；空闲时job/epoch/序号/generation均0。空闲复位不生成虚构作业终态。 |
| 2 RECOVERY_STATUS | data[143:8]=0，返回恢复状态；在内层软复位期间仍可访问。 |
| 3 RETRY_DRAIN | 仅QUARANTINE且隔离结果已被主机消费，data[143:8]=0；重新等待底层排空，安全复位，不为旧作业再次生成终态。 |

无活动作业返回0x105；忙返回0x106；身份/世代错误0x107；字段错误0x103；目标错误0x102；未知子命令0x101。RESULT已经转交主机时拒绝取消，不覆盖它。迟到故障会等待该回复接收并恢复组状态；有效终态不重复生成，未就绪RESULT查询不吞掉新的故障终态。

软恢复后必须使用大于历史水位的RELEASE epoch，水位在监督层保留，旧epoch拒绝。J仍受1..255原生epoch限制，不自动绕回。外部物理复位会清除整个控制域及水位；新的外部复位会话必须整体重建数据和部署。

## 状态与结果

NORMAL中原命令0..14沿用既有管理器；恢复期间命令9由监督层回答，命令10读取失败终态，其余操作除上述命令15外拒绝。恢复状态格式也可随时通过15/2读取：

| 位段 | 含义 |
| --- | --- |
| [2:0] / [5:3] | 当前内层image_valid / poison |
| 16 / 17 / 18 / 19 | 内层run_active / 未清义务或恢复中 / 有结果 / 隔离 |
| [22:20] / 23 / [31:24] | 恢复状态0..5 / 数据路径已静止 / 请求的reset mask（实际复位范围始终为全组） |
| [63:32] / [79:64] | epoch水位 / 原始恢复原因 |
| [111:80] / [143:112] | 当前内层已观察读/写字节；软复位后内层值清零 |
| [175:144] / [207:176] | 当前内层目的提交字数 / 匹配ACK握手数 |

失败RESULT沿用基础包job/epoch/序号/status和确认读写字节位置。status=11表示取消或运行中复位请求，0x200表示观察到组故障，0x201表示排空超时。error_pc/child_pc为0xffffffff、source=255表示监督层不伪造局控归因。扩展位282=恢复结果，283=隔离，284=本作业数据应视为可能部分写入而无效；[316:285]目的真实提交字数，[348:317]ACK握手数，[356:349]请求mask。其余未用位0。

恢复结果的溢出/饱和诊断位280/281未采集，profiles明确标为无效，保留0不能解释为已完成这两项诊断。普通运行RESULT合同不变。

ACK计数包含匹配的负向取消确认，不能作为成功写入数；实际写入以commit计数和确认写字节判断。确认写字节包含真实原生服务写回，以及在目的存储响应处计数的运输写，即使RECEIVE尚未执行也不漏记。正常排空结果为最终计数，隔离结果为超时时刻快照，后续底层仍可能完成，不能把该快照当作全部最终落存数量。失败结果保持到主机接受回复，只消费一次。

## 验证与时钟边界

恢复矩阵使用四类源、两PM后端、19类模式及三种初态/种子；正常回归另用既有七模式。覆盖取消各运输阶段、原生/PM故障、超时隔离/重试、源/目的复位请求、长回复背压、外部组复位、旧epoch ACK、错误取消身份、完成后拒绝取消，以及有效/未就绪RESULT与故障的两种竞争。未提交目的毒值保持，已提交完整128 bit数据在软复位后实际读回，再重装新任务核对。
