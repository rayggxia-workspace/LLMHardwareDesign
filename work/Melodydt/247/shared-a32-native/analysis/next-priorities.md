# run34 后的下一步建议（研究顺序，不是新实施）

依据：run34 最终 result.json，SHA-256 `dfd2271bccfd9c13e846fcc190e5fd0b2b321752c0c890e07e3ff3eb7957bce1`。本文使用已通过功能回执的纯 JSON 周期分析；原始日志和成果 SHA 由独立 receipt audit 核验。没有运行新实验，也不推算 token/s。

1. **先建立连续负载的原生周期分解，定位 LOAD 与命令调度。** 当前 A32 已把 A 握手拍数 1520→840、供数区间和 1552→904；但处理墙钟只少 294 拍，且 16 个场景虽供数缩短却处理周期不动。应记录每 P 的 A 最后一次接受、B 最后一次接受、LOAD join 完成、M start/finish、结果读回和 ACK 等待，再用连续多个 K 段/输出组的等工作负载验证。现有测试每次响应故意保持两拍背压，并串行读回结果，这些是功能验证行为；新的性能用例可以配置真实消费者就绪，但保留原功能回归。不能把人为测试等待误报为 RTL 可回收时间。

2. **下一项 RTL 候选优先检查 B 供数、LOAD join 以及命令连续发起，是否需要优化由上一步事件决定。** 例如 A8/B16、rows=3、tiles=4 场景 A feed 合计 26→16，而 LOAD 合计仍 44、处理仍 168 拍；A8/B8、rows=8、tiles=4 则 LOAD 合计 77→47、处理 329→314。前者说明其它就绪条件覆盖了 A 改善，后者说明足够长的 A 供数仍在关键路径。B 路径、join 和响应控制是明确需要检查的位置，尚未唯一定位其中哪一项占主导。可研究 B 预取/保持、跨 bank 准备与命令调度，须维持租约、有限信用、格式与标签正确性。

3. **M 算术吞吐优化排在连续负载分解之后；暂不优先继续加宽 A。** 四种格式下 M compute 周期均完全未变；S16 的较高算术成本会摊薄入口收益，但当前合计计数不是完整图的瓶颈证明。应先确认连续负载中 M 的忙碌占比，再选择计算流水、部分和或调度优化，计入新增面积与真实频率。当前32B入口已得到功能与有限微基准证据，继续扩宽到64/128B还需要新的硬件服务合同和实测收益，不能默认按带宽倍增。

CONTEXTS=0 与 8 的比较不能解读成“8 组部分和使硬件变慢”：当前两种 bench 分别执行整批 START 和逐行 context 命令/释放，命令数为 2560 与 3648，属于不同调度。应在各自相同工作合同内比较 A16/A32；两者每场景节省周期相等，而百分比因基数不同而不同。

`processing - compute/2`、`processing - load/2` 或其它区间差都不是已经可回收的时间：区间有并行、控制固定开销和观测边界差异。不得把这些差额直接变成下一轮预期加速率，亦不得用本轮 1.4%～2.0% 去乘旧条件模型 token/s。
