# PR #221：U 原生三源入口和同时 SEND 修复

2026-11-08（Asia/Shanghai）。Issue [#212](https://github.com/rayggxia-workspace/LLMHardwareDesign/issues/212)，PR [#221](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/221)。最终资格及交付摘要以 [机器索引](u-native-fix.json) 为准。

## 两处修复

- **同时 SEND**：每个 U 增加独立的 128 位 TX 保持槽。S 读响应被捕获后立即释放响应口，接收预约可以继续完成远端数据写入。保持槽及 SEND 完成仍等真实远端存储 ACK；没有用本地读完成代替远端确认。背压时保持数据稳定，复位清除旧传输。
- **普通三源 FMA**：生产路径中的旧原生服务适配器允许 U 的 E lane 0 使用三个源，继续把实际源数传给 E；缺少的源按零处理。N lane 1 仍最多两个源，非法 lane 仍拒绝。测试不再绕过这一入口。

两项共用于 U_128/U_64，P 和 C/F/J 不改。控制指令仍为已记录的 #195 原生服务子集；U_64 的紧凑取指来自 #180 固定提交 `b54531b3359167668f8e696c97bd5882a7bee473`，PM 和数据口仍 128 位。没有扩大为 #180 所有最新服务的覆盖声明。

## 功能证据

1. 旧最终 U 网表负对照作业 100024/100029 重现同时 SEND 看门狗超时；100025/100030 重现三源入口 status=5。这些是预期失败，未计入通过数。
2. `native_entry.sh` 作业 100033 用真实 SRAM、N/E 和生产入口验证 FMA 源数 0/1/2/3，结果为 0/0/6/11；严格检查读取数、写入数、SEND 数据和存储 ACK。N 三源及非法 lane 返回拒绝，且不发宏命令。
3. `native_replay.py` 用真实母控、双局控、两颗 U 和 SRAM，先预约双方接收，再用屏障迫使首轮双方同时发送。后续重新发送实际收到的 SRAM 数据，检查读写数据、握手和 192 字节确认量。普通 FMA 两源/三源都经过同一服务入口。
4. 正常、背压和中途复位各用三种初始化。复位前输入故意不同于复位后输入，防止旧 TX 槽数据侥幸通过。最终网表还覆盖正常、故障、背压故障以及 U_64 偶数长度和 legacy 镜像。

最终 U_128 网表 48 次、U_64 网表 78 次均全部通过；这些数字是通过的测试次数，不是通过率。镜像、描述符、测试输入、日志和最终网表 SHA 逐一绑定在各交付包中。
