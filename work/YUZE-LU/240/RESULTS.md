[Issue #240](https://github.com/rayggxia-workspace/LLMHardwareDesign/issues/240) / [PR #241](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/241)。源码：[systemc_block_study](../../../project/experiments/systemc_block_study/README.md)；[原诊断](DIAGNOSIS.md)；[输入/源清单](manifest.json)；[34 组结果](evidence/local/results.json)；[独立审计](evidence/local/audit.json)。

**本轮已实现独立 SystemC 架构模型并做三轮对照，尚未实现对应的新 RTL。** 顶层定制的方法不变；私有 S 每组仍为 16 KiB。以下新吞吐都是明确硬件假设下的预测，不是现有五类底座的实测成绩，也不是 #220 的 DP 算法收益。未修改 #220 或其他并行任务。

## 2. 三轮结果

均条件使用 300 MHz；只激活 P0、P1、U0。其他控制组未模拟执行，也没有增加共享大缓存。下面每一项是独立消融配置，完整 34 项在 JSON 中。

| 架构候选 | B1/S2 prefill token/s | context512 decode 预测 token/s |
|---|---:|---:|
| 新打包适配器/E32，现有 M 原语，K32、原 S/IO 预算 | 0.1471 | 未测此项 decode |
| 候选原生 S32 M，较低 S 延迟、128 位 IO | 0.4767 | 0.3515 |
| 同上，参考 512 位 S/MEM 接口、17.1 GB/s 聚合峰值 | 0.6655 | 0.4964 |
| 同上，适配 16 KiB 的较大 K 分片，W16 | 0.9484 | 0.6988 |
| 同上，假设 W8，激活/KV 仍 S32 | 1.1716 | 0.9717 |
| 再加 P 内流水和输入驻留，W8 | 1.9840 | 2.2740 |
| 再加 DMA 描述符并行在途，W8 | 2.1657 | 2.2201 |
| 再加 E32 II=1 与有限上下文，W8 | **2.8698** | **2.7146** |
| 相同最终方案，保留 W16 | **2.1073** | **1.6821** |

最终 W8 decode：context128 **2.9459**、context512 **2.7146**、context2048 **2.0957** token/s。数值图还未资格化，所以这些不是已生成正确文本的实测结果。

第二轮说明宏内供数/启动/合并很重要；第三轮说明增加队列并不单调提速：512 的纯 DMA 排队配置略慢，S 端口竞争和传输次序不能忽略。最后的 E32 流水减少了局部服务停顿。没有删除算子、把 S 设成无限、遗漏写确认，或把所有字节传输设为零周期。

## 3. 当前主要卡在哪里

最终 W8、context512：总时间 **0.368374988 s/token**。

| 阶段 | 秒/token | 总时间占比 |
|---|---:|---:|
| Dot，含供数、局部缓冲竞争及回写 | 0.306449 | 83.19% |
| SiLU/RoPE/倒数候选微程序 | 0.021494 | 5.83% |
| NExp | 0.018487 | 5.02% |
| 其他向量、归约、KV 与复制 | 0.021945 | 5.96% |

每 token 总线读写 **3,604,728,064 字节**，有效平均约 **9.79 GB/s**，相当于 17.1 GB/s 聚合峰值的约 57.2%。这是全程平均，不是实测 DDR 利用率，也不能据此归因到某一条真实通道。仍有有限请求、启动/尾部、方向切换及 S 竞争。

按当前流量，即使所有计算免费、总线始终满载，仍有 `T >= bytes/BW = 0.210802811 s/token`，即 **4.7438 token/s 上限**。因此当前配置不能靠提高 DP 搜索宽度达到 5 token/s。真正的执行只会更慢。最少要进一步减流量和服务停顿，或明确承担更大的接口预算；不能偷偷提高带宽。

输入驻留并非无效：在第二轮 W8 context512 中，读总线由约 4.736 GB 降到 3.584 GB，避免约 **1.152 GB/token** 的重复 A 搬入。容量不足的输入继续分片；输出和 KV 不会假装驻留于无限 S。静态矩阵 W8 权重读取下界约 **3.086 GB/token**；还没有达到一次权重流之外几乎零额外流量的状态。

## 4. 参考项目提供了什么

[openTPU](https://github.com/FeSens/openTPU#results) 的公开设备表列出 SmolLM3-3B INT8 5.00、Phi-4-mini 3.8B INT8 3.99 token/s。其平台使用两路 DDR3，聚合峰值 17.1 GB/s，并报告接近峰值的 decode 搬运。这里借鉴连续权重流、片内激活保存、向量单元和量化器；17.1 GB/s 只作为单列的参考预算，绝非本项目板卡实测。

[LLAccel 的架构](https://github.com/taisirhassan/llaccel#how-it-works) 提供分银行 SRAM、DMA 队列和信号量控制的思路。[RESULTS](https://github.com/taisirhassan/llaccel/blob/main/docs/RESULTS.md) 的证据针对 4 层、H128 的字符模型，不能当作 3B 板卡 token/s。它说明在途请求深度值得测，但没有证明越深越快。

本研究仍用 S32 激活/KV，W8 尚未量化验收；模型和执行范围也不同。**尚不能宣称完成“至少达到 FPGA”的同条件目标。** 下一轮需要固定同一 3–4B 模型、权重精度、context、计时范围和外存预算。现阶段不把不同精度、不同模型的横表当公平胜负。

## 5. 真正需要修改的层级

| 层级 | 候选实现合同 | 当前资格 |
|---|---|---|
| P 的 M/适配器 | 原生 S32 乘加或等价高效实现；96 位全 K 累加，最后一次 RNE/饱和；持续供数；A256/B512 接口；两缓冲和真实 ACK | SystemC 与数学小例；新 RTL、面积、功耗、300 MHz 均待验证 |
| P 的局部数据组织 | 按 S 剩余空间同时选 K 分片和 A 驻留；行切换前排空两个旧缓冲；不可固定声称都命中 | 已模型化，实际 S 地址/调度微程序待绑定 |
| U 的 E32 | 四个 S32 lane；流水 II=1、延迟6；16个 packet 上下文；中间值占本地寄存器，逐步保留舍入语义 | 仅候选，不能继承旧 E 的小面积和物理资格 |
| 局部 S | 容量仍16KiB；参考配置需512位聚合访问及银行/客户端仲裁 | 现有16KiB S 的验收不覆盖这个新端口；要重做 RTL 和物理 |
| MEM/DMA | 64字节 beat、32 beat credit、32描述符 credit、分片/步幅访问、独立完成、**64位字节写掩码**或等价不覆写邻数据的机制 | 研究控制器；当前接口通常不是此配置，需新适配器/RTL；未标定 DDR |
| 精度/编译前端 | 若采用 INT8 权重或更低激活流量，明确 scale、量化/反量化服务与误差验收 | 未完成，不能只改一个带宽数字当支持 |

所有新算术、选择、缓冲和驱动均须在新版本 M1–M10 冻结前实现。M11/M12 只做允许的端点连接；不能在当前冻结底座上加金属就获得新逻辑。Block 仍是局控分组；宏接口、必要适配器、控制线和约束由共同底座索引描述，不新增五个大硬框。

下一步优先实现/校准 P 的连续供数和宽累加、E32 流水及必要 S/MEM 适配，逐项核算面积、端点接入和时序。把**资格化后的**服务表交给 #220 评分，再在同一硬件、同一算子图下比较贪心/DP，单独核算算法收益。本 PR 没有借硬件升级申领约20%的 DP 优化目标。

## 6. 验证、复现与未完成项

- Windows GCC14.2、SystemC3.0.2：`-std=c++17 -O2 -Wall -Wextra -Werror` 通过；34场景、34项独立工作/流量/容量审计、5冒烟、4资源/ACK/负向控制通过。
- 独立 Python 无界整数 oracle 对 C++ 分量重构、96位界限、RNE/饱和：225例、56261个乘积通过；不是整模型数值验收。
- 原 M RTL 与本 PR 基线 main 快照同 SHA `5825adcd3364d4315afd1aa4addae85379fb36df2802ca8ab60026e0b0f44d1e`。Verilator5.042 的 R=1/2/8、K=1/8/32 九例通过，见 [原生回执](evidence/native/m-profile.log)。这只校准旧 M 的 Execute，不校准候选原生 S32 M、整个适配器或物理频率。
- 新模型的完整图数值、真实 KV decode、母控/局控指令联合执行、全芯片布局布线与实际能耗：**未执行**。
- 没有可靠的宏/SRAM/DRAM 每事件能量标定，能耗结果为 null；不能把周期数冒充焦耳。已有流量与算术工作量可供后续有来源的能量模型使用。
