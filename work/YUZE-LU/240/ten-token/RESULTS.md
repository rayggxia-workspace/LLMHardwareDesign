# 10 token/s 双路线：条件计时与独立 RTL 证据

关联 [Issue240](https://github.com/rayggxia-workspace/LLMHardwareDesign/issues/240) / [PR241](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/241)。2026-11-09，目标仍为 **10 token/s**；用户发送的“8”为误触。成果处于研究/实现中，不能认定现有底座已经达到目标。

## 主要结果

Qwen2.5-3B，B1，36层，H2048、FFN11008、16Q/2KV heads，条件300 MHz。decode 是包含 KV 大小和写入确认的**配置派生工作量图**，没有加载真实新量化权重生成 token；prefill 是既有完整 B1/S2 整数 DAG 的计时。下表都不是整模型 RTL 或实机吞吐。

102.4候选每步约3.7335 GB总总线搬运，平均约40.06 GB/s，明显低于102.4 GB/s峰值；约63%时间仍在Dot及供数/回写，约37%在其余服务。两个通道实际约2.423/1.311 GB，分配不平衡。当前跨组依然经外存，未虚构已布通的宏间直连。因此仍有值得优化的调度、跨算子驻留和布线空间。

按3,085,938,688参数每个token读一次W8的必要条件，仅权重就需约3.086 GB；17.1 GB/s下理想上限约5.54 token/s。10 token/s需要改变权重流量或带宽。固定预算压缩路线尚未解决，不能把W4/W2的数值资格省略，也不能忽略scale、索引、解包器和额外状态。

## 与预制底座合同的关系

保留`five-block-v1/2026-11-07`的独立叶宏、固定局控归属、九组资源和顶层M11/M12连接方法；P/U/C/F/J不变成五种大物理硬块。原生产RTL和已验收底座没有被替换。

| 主要候选资源 | 明确成本/约束 |
|---|---|
| 激活3P和1U | 原九组中有3P，额外启用P2；活跃私有容量64 KiB，整版九组仍需计144 KiB及控制存储 |
| 每组16 KiB | P双B银行与A/工作区/输出窗口合计受16 KiB限制；U缓存12 KiB加4 KiB工作区；无跨组共享S |
| DMA聚合beat256 B | 2048位级别的控制器内数据接口，两个通道合计102.4 GB/s；不是17.1 GB/s旧控制器 |
| 通用S服务128 B/拍 | 1024位新服务端口；旧16 KiB宏的面积/时序资格不转移 |
| 两个独立B银行 | 每银行128 B/拍，单端口写/读互斥、消费完才重填；必须预制端口、存储划分与仲裁 |
| 新K16 M | A512/B1024位、输出256位、8个行上下文、96位累加；3颗合计115.2 G个字节乘积/秒理论峰值 |
| E8 S32服务 | II1、延迟6、最多16个packet上下文是候选假设，尚无对应联合RTL/物理；并非旧S16 E |
| N批处理适配 | 接独立原生N的命令/响应接口，必须独占一次batch并与其他客户端仲裁 |

等16 KiB是**容量预算**，不是现有S硬宏不动就能多出银行和宽端口。若保留整颗原16 KiB S再加B银行，新增存储必须另计；那属于另一配置。新逻辑/端口要在新版本M1–M10冻结前存在，M11/M12不能添加乘法器、选择器、缓存或再定时寄存器。真实端点接入、线宽、负载和时序失败后，必须回改映射/时序；不能从当前预测直接得到可部署程序或拓扑。

## 已落到RTL的部分

**N批处理：** `nexp_batch_adapter.sv`连接未改的独立N。原scalar服务是`exp(x-max(x,0))`；batch先将各S16输入夹到≤0，用全零统计得到max0，再执行相同N指数。没有把正数混在一组最大值里改变语义。Begin/Stats/Finalize/Exp共四命令，输入n≤8；后继背压时保持结果。

原生Verilator作业101746（源9b4367a2c）遍历全部65536种S16值，并测尾片、非法count、复位和背压，**66440值/8419帧**通过与原五命令scalar序列的逐位比较。n1/2、3/4、5/6、7/8分别13、17、21、25拍。模型还单列夹取/打包服务与真实S访问，没有先发布输出再补算时间。[原生日志](evidence/native-n/nexp-native-run.log)。

**M候选：** `m_s32_stream_candidate.sv`是新独立叶宏ABI，四级寄存，显式平衡归约树；8行96位上下文，S16/S32 B用字节平面精确重构，最终RNE/S32饱和。输出背压冻结流水，输入不能继续覆盖。`m_vectors.py`用Python无界整数产生独立参考。

原生作业101753（源1bc6e0b04）K16/K32分别处理19240/9685包，各**117个完整Dot、4个错误响应**，k从1至11008、N尾片1/3/8、S8/S16/S32 B、交错上下文、随机输出背压；242个最终响应逐位通过。连续31拍II1被实际观察，不是由公式推断。[K16](evidence/native-m/vectors16/verification.json)、[K32](evidence/native-m/vectors32/verification.json)。只证明这些RTL核的功能与无物理延迟的拍间吞吐，**没有300 MHz STA、整模型或联合控制验收**。

模型的`M_commands`仍是研究中的分片服务计数，不是新RTL的逐字节平面命令数，也不是#180 ISA指令数量。模型按实际平面数计compute时间；后续程序生成需展开并校验精确命令数和真实依赖。

## 验证、失败尝试和剩余工作

- 最终24项SystemC独立工作量/权重下界/容量/时钟/通道守恒审计、61项尾片/跨行/N缓存寿命/缺失写确认/非法配置检查通过。原P/U容量、32个credit和写ACK覆盖约束保留。
- 旧N批处理计价/宽整数单遍假设的早期13项以及静态1:2:1通道分配4项保留在`evidence/prior-rounds/`；**不能与修正后最终数字混用**。通道分配退化是实际反例，不能只公布最快方案。
- 原生首次8G内存申请被集群配置拒绝，没有作业；101743因VERILATOR_ROOT设置错误失败；101745、101746成功。M的101750通过独立整数参考，改平衡树/连续输入后由101753重新验证。准备目录04归档层级错误，未提交作业；不写成通过。
- 本地SystemC：GCC14.2、SystemC3.0.2，C++17/O2/Wall/Wextra/Werror；原生RTL：Verilator5.042、GCC11.4、ORFS26Q1容器、Slurm c64/4核。具体SHA与位置见manifest及README。
- 完整真实权重W8质量、真实KV连续生成、E32与有限packet scoreboard、B银行/SRAM/DMA仲裁、母控/局控程序集成，以及新端点/布局/提取时序均未完成。候选SiLU、RoPE、倒数配方也需全图数值验收。
- 没有标定的pJ/运算、pJ/bit或SRAM能量表，故只保留工作量/搬运计数，不输出伪精确J/token。能耗模型应以实际宏/存储/PHY版本表征并单列静态功耗。

## 用户已有对照的正确用法

用户自己的短测中，openTPU INT8为5.211746 token/s，原生RTL/真实权重/KV及ISA词表一致；FP4/headINT8为8.840913，但两步cosine约0.7747。LLAccel最快已完成约1.765797，整数执行一致但两步cosine约0.2451、top1 0/2，不能作为等质量推理优胜者。

这些测试实际只有Hello一token提示词，计位置1的一步decode，不是context512。openTPU约528 KiB逻辑ACT+TMEM（不含复制/FIFO）与本研究64 KiB活跃私有S差异很大，DRAM模型和频率也不同。当前13.4852的context2预测不能写成战胜5.211746的真实RTL推理。原始证据在本地`D:/Data/电路实验/peer-systemc-20261109`、服务器自有`peer-systemc-20261109-side-001`，尚未将完整peer大包纳入本PR。

下一道验收应先冻结量化/整数数值合同，再把102.4候选的M、E、N、存储/DMA和局控连接为同一可执行切片，使用同一生成程序/拓扑做SystemC与RTL事件及数值对照。完整模型和提取物理结果通过前，Issue240保持进行中，PR保持draft，不自合并。
