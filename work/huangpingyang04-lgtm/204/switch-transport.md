# Qwen 九实例传输与 C0 四选一

任务 [#204](https://github.com/rayggxia-workspace/LLMHardwareDesign/issues/204)，草稿 [#206](https://github.com/rayggxia-workspace/LLMHardwareDesign/pull/206)。接续 #176 的 23 条 Qwen 候选传输和 #194 的宏版图。按用户选择，已有计算宏内部连接留在原生层，新增上层布线连接传输模块与计算宏。

## 实现与范围

- C0 有 P2、U0、U1、F0 四个接线输入。一次只选一路。C0 的 SRAM 写确认返回给所选发送端，随后才能释放源数据。[C0 实现](../../../project/rtl/qwen_transport/c0_receive.sv)
- 九实例版按实际的 P/J SRAM 请求/响应和 U/C/F 的 TX/RX 信号接入，检查 23 条许可关系。仲裁由传输命令选择，硬件每次只保留一笔 128 位传输。目的地址与接收预约来自控制器。[九实例实现](../../../project/rtl/qwen_transport/nine_transport.sv)
- 布线输入包括跨宏数据、地址和握手，C0 版 711 根，九实例版 2,491 根。每根有两个实际 M10 端点和唯一输出驱动。C0 版另外 30 个传输模块控制端点，九实例版另外 44 个传输模块控制端点，属于父层控制、预约、时钟及复位的接入边界。外存权重/KV/状态及系统供电与时钟另行集成。

## 功能验证

Slurm `98443`，Verilator 5.042，两种配置均成功退出。C0 版逐一测试四个来源。九实例版覆盖 9×9 源宿组合及两个越界选择，许可路径进行真实数据比较，其余要求拒绝。覆盖读等待、接收预约、延迟写确认和未确认时的协同复位。端口驱动由独立协议模型提供。源提交 `96889ecf8d72eee514ea1a98beb4f2af84b1a367`。[测试代码](../../../project/experiments/nine_block_route/tb_qwen_transport.sv)

Slurm `98492` 对 C0 `98486` 和九实例 `98450` 的两份实际原生布线后门级网表执行同样的回归，两种配置均通过。编译使用 Nangate45 Liberty 生成的功能单元模型，按零延迟验证。[网表、日志及原件摘要](switch-native-receipts.json)

## 上层布线对照

服务器已完成的 M11/M12 构造搜索中，C0 的最佳无规则错误结果为 473/711，九实例最佳为 1,132/2,491。这里的零错误指已布部分，完整候选仍有未连网。四个 OpenROAD 详细路由作业 `98461`、`98462`、`98467`、`98468` 在历史快照中还在运行。两侧通道方案通过整版验收后，结束了这些旧对照作业。[逐作业状态和绑定快照](switch-upper-snapshot.json)

### C0 接收侧

三种摆位的选择器到 C0 连线均通过。每种有 142 根，含 128 根数据、10 根地址和 4 根握手。所有网均从选择器的实际 M10 落点到 C0 的实际 M10 落点，并通过短接、宽度、间距、通孔包围和 KLayout GDS 回读检查。这是单独的 C0 接收侧对照，下方的九宏版包含所有传输源和接收端。[DEF/GDS 存档位置、校验和与逐摆位回执](c0-rx-routed.json)

上层详细路由输出由独立 [OpenDB 验收入口](../../../project/experiments/nine_block_route/run_switch_check.sh) 回读。该验收按实际线段检查连通和几何，并将 via10 落点叠回最终保护版的原生 GDS。作业 `98516` 对已有 290 网版图的对照为 290/290、零错误。作业 `98517`–`98520` 分别在四个详细路由作业正常退出后自动验收。[OpenDB 对照结果](switch-odb-check-control.json)

## 九宏 M11/M12 联合布线验收

将九个计算宏分置在传输模块两侧，为每个宏分配独立的走线通道。保持 #194 的计算宏内部版图和真实 M10 端口，用重新排布的传输模块接点承接这些通道。组合版图边界为 8,572 × 12,216 µm，传输模块为 1,344 × 11,960 µm。通道构造采用带容量的两层轨道图和交错的 via11 落点。

| 作业 | 结果 |
| --- | --- |
| `98662` | 9 个宏的 2,491 根线全部布通，几何预检为零错误 |
| `98699` | 从传输模块原生 CTS 数据库回读，2,491 个 M10 接点矩形全部匹配 |
| `98673` | 生成新的原生传输模块 LEF、ODB、GDS 和网表，原生详细布线最终零违规 |
| `98674` | 绑定真实落点后为 2,491/2,491、零几何错误。KLayout 回读上层 GDS 和实际原生 M10 均通过。DEF 导回 OpenDB，2,491 网、4,982 个连接 |
| `98780` | 读取从上一步 OpenDB 导出的矩形，独立逐网连通验收 2,491/2,491、零错误 |
| `98677` | 原生布线后零延迟门级回归通过 |
| `98675` | 传输模块独立原生全 GDS 规则复核在本次归档时仍运行 |

上层通过宽度、间距、短接、通孔包围及完整连通验收。可用 `routed.odb` 或同版 `route.def`、LEF 进入 #202 的 M11/M12 寄生提取流程。研究版上层掩模为 `upper-only.gds`。全部路径、输入版图、技术 LEF 及 SHA-256 见 [整版物理回执](nine-upper-routed.json)。

本次覆盖九个计算宏与传输模块之间的信号。父层控制、存储和系统集成属于另外的边界。300 MHz 约束下，传输模块的原生布线后 WNS 为 −7.74 ns，时序还未闭合。

复跑依次使用 [通道规划](../../../project/experiments/nine_block_route/channel_plan.py)、[原生构建](../../../project/experiments/nine_block_route/run_switch.sh) 的 `pin-plan.json` 参数和 [上层回读](../../../project/experiments/nine_block_route/run_channel_verify.sh)。先以 `g++ -std=c++11 -O2` 编译 [通道求解器](../../../project/experiments/nine_block_route/channel_escape.cc)，再将可执行文件和原版输入目录交给规划脚本。`98649` 的 FastRoute 对照报边容量告警后退出，最终结果来自两侧通道方案。
